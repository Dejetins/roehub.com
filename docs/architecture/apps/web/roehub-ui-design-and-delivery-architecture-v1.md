# Roehub — архитектура проектирования и поставки интерфейса v1

Документ фиксирует принятый процесс проектирования локальной платформы и публичного сайта от реестра поверхностей через отдельные файлы Penpot до независимых рабочих сборок.

## Статус

- Статус: `accepted architecture`.
- Инструментальная поправка от `2026-07-22`: все будущие инструкции Penpot в
  этом документе заменены для Roehub контрактом
  [`roehub-figma-design-delivery-standard-v1.md`](../../ui/roehub-figma-design-delivery-standard-v1.md).
  Penpot-разделы ниже сохранены только как историческое описание прежнего
  процесса и не разрешают новые записи. Custometry эта поправка не затрагивает.
- Для authenticated local-platform UI последовательность design-system → full
  Penpot → implementation заменена принятым route-bounded Linear-workspace
  переходом в
  [актуальной specification](../../../../.codex/delivery/specs/roehub-linear-workspace-ui-transition.md).
  Этот документ сохраняется как historical process evidence; backend и public
  website границы не меняются.
- Документ является архитектурным контрактом процесса, но не планом
  реализации, журналом, пакетом промтов или разрешением на изменение Penpot,
  кода, публикацию и развёртывание.
- Одна готовая задача остаётся одной единицей исполнения.

## Цель

Получить полный, проверяемый и воспроизводимый интерфейс Roehub без смешивания:

- локальной самостоятельно развёртываемой платформы;
- публичного сайта `roehub.com`;
- общей дизайн-системы;
- исторического SSR-интерфейса и исторического React-прототипа;
- дизайна и доказательств работающего браузерного поведения.

## Контекст

Текущие источники фактов:

- [`roehub-product-transformation-requirements-v1.md`](../../platform/roehub-product-transformation-requirements-v1.md)
  — принятые продуктовые требования;
- `apps/web/main/app.py`, `apps/web/templates/`, `apps/web/dist/` — действующий
  SSR-интерфейс, маршруты, состояния, локализация и граница одного источника;
- `prototypes/roehub-v2/` — исторический интерактивный прототип, а не целевой
  код;
- `apps/api/routes/` и действующие DTO — серверные возможности и ограничения;
- исторические принятые отчёты Web, identity, market data, backtest, live
  execution и self-hosted — свидетельства реализованного поведения.

Канонического реестра всех экранов, состояний, ролей и пользовательских путей
пока нет. До его создания нельзя считать прежний прототип или старый Penpot-
файл полной картой продукта.

## Охват

- реестр маршрутов, поверхностей, состояний, ролей и пользовательских путей;
- общая дизайн-система Roehub;
- отдельное проектирование локальной платформы;
- отдельное проектирование публичного сайта;
- трассировка Penpot-поверхностей к рабочему коду и браузерным доказательствам;
- целевая структура клиентского рабочего пространства;
- порядок завершения документации и снимков интерфейса.

## Что не входит

- реализация нового клиентского кода;
- создание или изменение файлов Penpot;
- выбор поставщика размещения, базы данных или почтовой доставки публичного
  сайта;
- выпуск, публикация или развёртывание;
- восстановление прежних 13 блоков, журналов или пакетов промтов;
- телефонный интерфейс локальной платформы.

## 1. Канонические файлы Penpot

Пользователь создаёт в Penpot три файла с точными именами:

1. `Roehub — Design System`
2. `Roehub — Self-Hosted Platform`
3. `Roehub.com — Public Website`

Правила зависимости:

- `Roehub — Design System` является единственной общей библиотекой Roehub;
- `Roehub — Self-Hosted Platform` подключает общую библиотеку, но не файл
  публичного сайта;
- `Roehub.com — Public Website` подключает общую библиотеку, но не файл
  платформы;
- файл Custometry может служить визуальным и техническим образцом, но не
  подключается как обязательная библиотека Roehub;
- каждое задание Penpot работает только с явно названным и подключённым файлом;
- агент проектирует, пользователь принимает результат или возвращает
  замечания; метаданные владельцев, редакторов и ревьюеров не являются
  условием работы.

### `Roehub — Design System`

Файл владеет:

- базовыми и семантическими токенами;
- шестью темами `abyss`, `graphite`, `slate`, `frost`, `paper`, `sand`;
- типографикой, сеткой, отступами, радиусами и движением;
- компонентами ввода, навигации, таблиц, диалогов и обратной связи;
- шаблонами Apache ECharts, табличными альтернативами, прогрессом и ETA;
- состояниями доступности, фокуса, клавиатурного управления и уменьшения
  движения.

### `Roehub — Self-Hosted Platform`

Файл владеет только локальной платформой и размерами `820`, `1024`, `1440`:

- входом, первым запуском и восстановлением;
- обзором, каталогом данных и подключениями;
- бектестами, стратегиями, исполнением и моделями;
- мониторингом, настройками и администрированием;
- локальной документацией и инструкциями;
- системными состояниями, диалогами и сквозными пользовательскими путями.

### `Roehub.com — Public Website`

Файл владеет только публичной поверхностью, включая телефонный размер `390`:

- главной страницей и описанием возможностей;
- самостоятельной установкой;
- документацией;
- историей выпусков, актуальным выпуском и загрузками;
- входом и минимальной учётной записью публичного сайта;
- будущей демонстрацией;
- безопасностью, сообществом, поддержкой и юридическими страницами;
- поисковыми и социальными изображениями.

## 2. Источники истины

| Поверхность | Канонический источник |
|---|---|
| Продуктовый результат | `roehub-product-transformation-requirements-v1.md` |
| Маршруты, роли и серверное поведение | текущий код, API и принятые контракты |
| Утверждённый визуальный результат | соответствующий файл Penpot и его именованная версия |
| Токены рабочей сборки | версионируемые пакеты репозитория после переноса из утверждённого дизайна |
| Работающее поведение | клиентский код, API и реальные браузерные доказательства |
| Публичный выпуск | SemVer из `pyproject.toml`, Git tag и GitHub Release |

Penpot не является доказательством авторизации, API, хранения, браузерной
доступности, производительности или выполнения операции.

## 3. Последовательность поставки

### Шаг 1. Инвентаризация

Создать реестр действующих и целевых:

- маршрутов;
- экранов и вложенных рабочих областей;
- состояний;
- ролей и действий;
- API и источников данных;
- пользовательских путей;
- публичных страниц и содержания.

### Шаг 2. Информационная архитектура

Утвердить навигацию, главный объект каждого экрана, переходы между
исследованием, бектестом, стратегией и исполнением, первый запуск и карту
публичного сайта.

### Шаг 3. Общая дизайн-система

Сначала создать библиотеку, затем проверить несколько представительных экранов
и все шесть тем. Не требуется дублировать каждый экран во всех темах: темы
распространяются через токены, а представительная матрица подтверждает их
корректность.

### Шаг 4. Полный дизайн локальной платформы

В одном файле платформы, но отдельными ограниченными задачами, закрыть:

1. оболочку, вход и первый запуск;
2. обзор, данные и подключения;
3. бектесты и модели;
4. стратегии и исполнение;
5. мониторинг, настройки и администрирование;
6. локальную документацию, ошибки и системные состояния.

Реализация платформы начинается только после полной продуктовой приёмки этого
файла.

### Шаг 5. Клиентская основа

Целевая структура:

```text
apps/
  web/                 существующий сервер и same-origin шлюз
  platform-web/        новый клиент локальной платформы
  site/                отдельная сборка публичного roehub.com

packages/
  tokens/
  ui/
  charts/
  localization/
  web-contracts/
```

`apps/platform-web` и `apps/site` не импортируют код друг друга. Общими могут
быть только явно выделенные пакеты `@roehub/*`.

### Шаг 6. Вертикальный перенос платформы

Код переносится законченными пользовательскими путями, а не набором несвязанных
страниц. Каждая задача доказывает работу в реальном браузере на `820`, `1024`,
`1440`, доступность, роли, ошибки и соответствие утверждённому Penpot.

### Шаг 7. Стабилизация

Перед окончательным проектированием публичного сайта необходимы стабильные
маршруты, тексты, Apache ECharts, прогресс и ETA, состояния ошибок,
детерминированные демонстрационные данные и эталонные снимки.

### Шаг 8. Публичный сайт и документация

После стабилизации платформы проектируются `Roehub.com — Public Website`,
реальные снимки, окончательная документация и отдельная сборка `apps/site`.

## 4. Минимальная трассировка дизайна

Для каждой поверхности хранится компактное соответствие:

- `surface_id`;
- маршрут;
- роль;
- состояния;
- размеры;
- `penpot_file_id`, `penpot_page_id`, `penpot_board_id`;
- продуктовый статус;
- путь реализации;
- браузерное доказательство.

Это не журнал исполнения и не второй источник статуса задачи.

## 5. Границы приёмки

### Дизайн готов

- покрыты все элементы принятого реестра;
- нет неизвестных маршрутов или пользовательских переходов;
- явно показаны загрузка, пустой результат, ошибка, ограничение прав,
  устаревшие данные, потеря сеанса и восстановление;
- проверены требуемые размеры и темы;
- компоненты используют библиотеку, а не локальные несвязанные копии;
- пользователь утвердил именованную версию.

### Реализация готова

- маршрут и состояние связаны с утверждённой поверхностью;
- браузерная проверка использует реальное приложение и подходящие тестовые
  данные;
- проверены клавиатура, контраст, масштабирование и уменьшение движения;
- API, права и ошибки не подменены макетами;
- визуальное сравнение не скрывает функциональные расхождения.

## Риски и открытые вопросы

- Текущий React-прототип содержит телефонные решения локальной платформы и не
  может быть перенесён как готовый контракт.
- Публичный сайт имеет отдельную центральную учётную запись, поэтому требует
  собственной модели приватности и удаления данных.
- В репозитории пока нет опубликованных GitHub Releases; история выпусков сайта
  зависит от появления канонического процесса публикации.
- Подробный выбор серверной реализации авторизации публичного сайта делается
  отдельной задачей после принятия продуктовой модели.
