# Roehub UI surface inventory v1

A traceable inventory of current local-platform surfaces and the separately
specified public-site target surface map.

## Status and boundary

- Status: `accepted inventory`.
- Ticket: `ROEHUB-UI-INVENTORY-2026-07-20`.
- Evidence date: `2026-07-20`.
- This is an inventory, not a visual design program, delivery plan, or
  implementation authority. No design resource was changed.
- The current SSR Web service is the authority for implemented local behaviour.
  Product and public-site documents are authority only for their labelled target
  requirements. The removed `prototypes/roehub-v2/` is available only in Git
  history at the accepted inventory baseline and never implementation or visual
  authority.

The companion registries are [local platform registry](roehub-ui-surface-registry-v1.json)
and [public-site registry](roehub-public-site-surface-registry-v1.json). They
are the complete machine-readable list of surfaces, route patterns, API
bindings, roles, mutations, freshness fields, states, gaps, and journeys.

## Roles and compatibility

Current SSR makes a binary authenticated-user gate and receives `user_id` and
`paid_level`. It does not itself establish the target owner, administrator,
operator, researcher/trader, read-only, or distinct `installation_owner`
matrix. The local registry therefore marks that matrix `target_not_implemented`
instead of presenting it as current access control.

| Requirement | Current evidence | Inventory classification |
|---|---|---|
| `/models` is canonical models workspace | The route exists, but renders `pages/strategies.html` with `strategy_initial_mode=rl_ml`. `/strategies?mode=rl_ml` is still accepted by the generic query handling. | Current compatibility alias is observed; target `308` from old alias is `target_not_implemented`. |
| Canonical local runbook route | Legacy `/runbooks/{runbook_id}` is implemented and protected. | `/docs/operator/runbooks/{runbook_id}/` and later `308` are `target_not_implemented`. |
| New backtest data modes | Current creation uses artifact-oriented endpoints and the requirements identify `direct_db` as not implemented. | `auto` and `direct_db` target behaviour are not represented as current API behaviour. |
| Local first launch | Local auth JavaScript includes passkey bootstrap options/completion, but the inspected current Web route set has no full owner + organisation + truthful catalogue journey. | `target_not_implemented`; a product/API task is required. |
| Local mobile UI | Current SSR shell contains mobile navigation CSS/markup. | It is an observed legacy implementation detail, not acceptance for the `820/1024/1440` target-only local-platform scope. |

## Canonical journeys

| Journey | Current path and evidence | Target-only / unresolved boundary |
|---|---|---|
| Sign in and continue | `/login?next=…` → local/OIDC auth endpoints → protected workspace; `next` is sanitised. | Recovery choice and owner bootstrap must remain local and avoid manual OpenBao lifecycle management. |
| First launch | Auth asset exposes local bootstrap; dashboard points to data onboarding. | Owner, organisation, passkey, truthful catalogue and skippable selection are not one implemented journey. |
| Select market data | Dashboard link → Settings market-data tab → markets/catalog/selections API. | Stable snapshot/cursor, provider segment and full supported catalogue are target requirements. |
| Add or maintain exchange connection | Settings/Connections → exchange modal → account connection API. | Target role split and secret-display policy must be proven by a later implementation task. |
| Configure and run backtest | `/backtests/new` → runtime defaults/preflight → create job → workstation refresh. | `auto`/`direct_db` modes and calibrated ETA proof are incomplete. |
| Inspect result and form strategy | Backtest job/variant detail → strategy creation/launch endpoints. | Product decision is still needed for final promotion criteria and safe defaults. |
| Create, modify, and control strategy | Strategies list/detail → CRUD, run/stop/restart/manual action endpoints. | Target roles and operator-safe stop/reconciliation are not fully demonstrated by current SSR. |
| Operate live execution | Strategies dashboard exposes live profile, runtime, paper accounting, signal journal, execution outcomes; execution ingress API exists. | Read-model availability does not prove an end-user live-operation workflow across roles. |
| Inspect models | `/models` → strategies dashboard `rl_ml` mode. | Dedicated canonical model registry with promotion/rollback semantics is target-only despite the route. |
| Monitor and follow runbook | `/monitoring` → dashboard summary → health/alerts → admin-linked local runbook. | Functional service grouping and safe role-scoped remediation need a later task. |
| Administer and recover | `/admin` → snapshot/operation API and confirmation dialog. | Physical installation limits, backups, updates, recovery authority and rollback evidence require product/implementation scope. |
| Read local documentation | Legacy runbook route uses installed local Markdown. | Canonical versioned `/docs/operator/runbooks/{runbook_id}/` route, visibility policy and `403` presentation are pending. |

## Gaps and required product decisions

| Severity | Confidence | Gap / unknown | Impact | Smallest required decision or follow-up |
|---|---|---|---|---|
| High | High | Full first-launch owner/organisation/recovery and catalogue contract is not implemented as one routeable journey. | A future UI could imply a usable self-hosted bootstrap that the current API/path does not provide. | Select a bounded product/API ticket that fixes the owner bootstrap, organisation creation, truthful snapshot/cursor catalogue, and skip/recovery states. |
| High | High | Current Web does not prove the accepted target role matrix, especially `installation_owner` and operator safe actions. | UI-only role claims could authorize unsafe operational behaviour. | Define server-enforced capability mapping per surface before a new UI implementation claims those roles. |
| Medium | High | `/models` and runbooks have required canonical compatibility migrations that are not implemented. | Bookmarks and the target information architecture would drift. | Decide migration order and acceptance for `/strategies?mode=rl_ml` → `/models` and legacy runbook → canonical docs route. |
| Medium | High | Public site has no implementation, release history, privacy policy, retention/deletion implementation, or demo boundary. | A site implementation could blur trust, privacy, or distribution semantics. | Complete a separate public-site specification/implementation ticket; do not reuse local identity or operator content. |
| Medium | High | Current account-panel freshness is uneven, and strings such as `Prod` in the shell are display values rather than runtime proof. | Operators may mistake stale or decorative UI for runtime evidence. | Define consistent source/freshness contract and collect browser/runtime proof in the implementing ticket. |
| Low | High | Prototype has local mobile pages while the accepted local target excludes phone layouts. | Historical prototype content could be promoted accidentally into target scope. | Preserve it only as historical evidence; do not promote it to a target requirement. |

## Verification and cold review

- Route evidence: generated directly from `apps.web.main.app.create_app()` and
  cross-checked against `apps/web/main/app.py`.
- API/DTO evidence: `apps/api/main/app.py`, current route modules, UI DTOs,
  Web templates, and static page modules.
- Registry validation: `tests/unit/docs/test_roehub_ui_surface_inventory.py`
  checks JSON parsing, stable unique IDs, route/surface references, required
  evidence/status fields, local/public separation, and target traceability.
- Architecture index and project map are regenerated after the inventory files
  exist; `git diff --check` is also required.

Cold self-review verdict: `Release`. No contradictory accepted safety
requirement was found. The gaps above are classified rather than hidden; none
requires product-code mutation to make this inventory truthful. Browser/runtime
behaviour, target role enforcement, and all future public-site behaviour remain
unverified boundaries, not accepted implementation claims.
