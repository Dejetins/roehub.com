# Roehub — базовые требования к продуктовой трансформации v1

## Статус и назначение

- Статус: `accepted product requirements baseline`.
- Документ фиксирует результат, который должна получить самостоятельно
  разворачиваемая платформа Roehub.
- Документ не является планом реализации, журналом, пакетом промтов, задачей
  исполнения или разрешением на публикацию и развёртывание.
- Конкретная реализация начинается только из отдельно выбранной задачи по
  действующему глобальному контракту поставки.

## 1. Текущее состояние

- Основной Web-интерфейс использует `FastAPI`, `Jinja` и `HTMX`.
- Старый React-прототип удалён из живого дерева и доступен только в Git history;
  он не является производственным приложением или целевым контрактом.
- Сохранённый Backtests Workbench v23 по пути
  `.codex/delivery/evidence/roehub-ui-agent-governed-pilot/specimens/2026-08-03-linear-black-workbench-v23.html`
  принят пользователем как визуальный пилот. Его путь и содержимое сохраняются;
  повторная приёмка через отдельный процесс не требуется. Пилот не доказывает
  реализацию API или серверных операций.
- Производственные графики бектестов используют Lightweight Charts; Apache
  ECharts ещё не является общей платформой визуализации.
- Создание бектеста использует опубликованные артефакты и фиксирует
  `artifact_pin`; режим `direct_db` ещё не реализован.
- Бектест уже имеет вычисляемые `progress_percent` и ETA выполнения. Их
  точность, калибровка, представление очереди и пользовательское поведение
  требуют отдельной проверки.
- Маршрут `/models` уже существует.
- Репозиторий публичен под Apache License 2.0, версия продукта берётся из
  `pyproject.toml`, но опубликованных GitHub Releases пока нет; действующая
  автоматизация публикует контейнерный образ, а не пользовательский выпуск с
  историей и набором файлов.
- Реализация self-hosted платформы, организации, роли, локальная авторизация и
  исторические эксплуатационные контракты сохраняются как факты текущего кода.

## 2. Продуктовая модель

1. Roehub является самостоятельно разворачиваемой платформой, а не единым
   центральным сервером для всех пользователей.
2. Разработка, проверка и выпуск не зависят от Mac Studio, SSH, `launchd`,
   Monit, `/opt/roehub/app` или другого частного хоста.
3. Установка должна быть самостоятельной, воспроизводимой, обновляемой и
   восстанавливаемой без обязательной связи с `roehub.com`.
4. Изменение конкретной пользовательской установки всегда требует отдельного
   явного разрешения владельца этой установки.

## 3. Новый Web-интерфейс

1. Действующий интерфейс должен быть полностью переработан: меняются клиентский
   движок, информационная архитектура, визуальная система и пользовательские
   пути.
2. Целевой набор технологий выбирается из проверенного набора Custometry без
   зависимости времени выполнения от репозитория Custometry:
   - рабочее пространство pnpm;
   - React и TypeScript;
   - Vite;
   - React Router;
   - TanStack Query и TanStack Table;
   - `i18next` и `react-i18next`;
   - Zod и React Hook Form;
   - Lucide;
   - Vitest, Testing Library, Playwright и axe.
3. Roehub владеет собственными пакетами `@roehub/*`, контрактами, компонентами
   и жизненным циклом зависимостей.
4. Клиент работает через безопасную границу одного источника; существующие API,
   сессии, CSRF, права, недавняя повторная аутентификация и сокрытие секретов не
   ослабляются.
5. Существующие полезные URL и закладки сохраняются через совместимые маршруты
   или явные перенаправления.

## 4. Пользовательский опыт и дизайн

1. Принятая визуальная база — Backtests Workbench v23. Её дальнейшее развитие
   определяется пользовательской задачей. Прежний поэтапный процесс
   проектирования прекращён; новый процесс пока не выбран.
2. Локальная платформа проектируется для размеров `820`, `1024`, `1440`.
3. Телефонная версия `390`, отдельная мобильная навигация и мобильные копии
   экранов локальной платформы не входят в текущий объём работ. Это ограничение
   не распространяется на публичный `roehub.com`, который обязан иметь
   телефонную версию.
4. Набор тем, tokens, typography, spacing, component language и motion
   развивается из принятого пилота в рамках выбранной задачи. Шесть тем
   существующего SSR UI являются implementation evidence, а не обязательным
   будущим визуальным контрактом.
5. Все состояния должны быть спроектированы явно: загрузка, пустой результат,
   ошибка, недоступность, устаревшие данные, отсутствие прав, потеря сеанса,
   неизвестный результат операции и восстановление.
6. Доступность, клавиатурное управление, масштабирование, локализация `ru/en`,
   достаточный контраст и уменьшение движения являются обязательными.
7. Дизайн создаёт агент, пользователь проверяет законченные visual checkpoints
   и принимает их либо возвращает замечания. Персональные роли владельцев,
   редакторов и ревьюеров дизайн-файла не требуются.

## 5. Графики

1. Все новые продуктовые графики реализуются на Apache ECharts.
2. Графики должны единообразно поддерживать финансовые ряды, свечи, сделки,
   результаты бектестов, сравнения, мониторинг и работу в реальном времени.
3. Пользователь всегда видит единицы, источник, актуальность, часовой пояс,
   легенду и доступную табличную или текстовую альтернативу.
4. Плагины не получают возможность передавать произвольный JavaScript,
   HTML-подсказки или неограниченные параметры ECharts.
5. Производительность Canvas и SVG подтверждается измерениями на реальных
   характерных объёмах данных.

## 6. Первый запуск и данные

1. Первый запуск создаёт локального владельца установки и организацию через
   понятный пользовательский путь.
2. Основной способ входа — ключ доступа; резервные способы и восстановление не
   должны требовать ручного управления внутренним жизненным циклом OpenBao.
3. Пользователь выбирает биржи, рынки, инструменты и требуемую историю из
   полного правдивого каталога поддерживаемых возможностей.
4. Каталог разделяет биржу, рынок и сегмент провайдера, использует стабильный
   снимок и курсорную пагинацию и не представляет неподдерживаемый сегмент как
   готовый.
5. Выбор инструментов при первом запуске можно пропустить; интерфейс должен
   объяснить пустое состояние и позволить продолжить настройку позднее.

## 7. Режимы данных бектеста

Пользователь выбирает один из трёх понятных режимов:

- `auto` — использовать подходящий готовый артефакт, а при его отсутствии или
  непригодности безопасно перейти к расчёту из базы;
- `direct_db` — читать исходные данные из канонической базы и рассчитывать
  цены, сигналы, SL/TP, funding и необходимые отображения без обязательных
  предварительных `.npy`;
- `artifact` — явно использовать совместимый опубликованный набор артефактов.

Общие требования:

1. Все режимы используют общий вычислительный смысл и проверяемые правила
   сопоставимости.
2. Для каждого запуска сохраняется неизменяемый снимок входных данных и
   идентичности расчёта, достаточный для воспроизведения без обязательного
   предварительного `.npy`-набора.
3. Режим, источник, актуальность, покрытие и причина автоматического выбора
   видимы пользователю.
4. Сравнение `direct_db` и `artifact` подтверждает допустимый уровень
   эквивалентности до переключения поведения по умолчанию.

## 8. Прогресс и ETA

1. Активный бектест показывает настоящий измеримый прогресс от `0%` до `100%`,
   основанный на выполненных единицах работы, а не на декоративном таймере.
2. После завершения полоса активного прогресса скрывается; итоговый статус и
   продолжительность остаются в истории задания.
3. ETA очереди и ETA выполнения различаются и не объединяются в вводящее в
   заблуждение значение.
4. ETA показывается только при достаточной уверенности, регулярно
   перекалибровывается по фактическим заданиям и явно сообщает отсутствие
   надёжной оценки.
5. Отмена, повтор, восстановление процесса и потеря сигнала прогресса не должны
   приводить к ложным `100%` или успеху.

## 9. Управление ресурсами

1. Владелец или администратор задаёт физические пределы установки.
2. Обычный пользователь управляет своим заданием только внутри этих пределов.
3. Бектесты и создание артефактов имеют раздельные бюджеты процессора, памяти,
   параллелизма, очереди и времени выполнения.
4. Пользователь видит выбранный профиль, ожидаемое влияние и причину отказа в
   запуске.
5. Значения по умолчанию безопасны для локальной установки и подтверждаются
   измерениями, а не предположениями.

## 10. Мониторинг и администрирование

1. Внутренние сервисы группируются по понятной функции, например: основа
   платформы, данные, вычисления, торговля, безопасность и расширения.
2. Общий широкий список всех процессов не является основным пользовательским
   представлением.
3. Экран различает готовность, доступность, деградацию, актуальность данных,
   влияние на пользователя и зависимости.
4. Для проблемы доступны понятное объяснение, связанная инструкция и безопасное
   действие в пределах роли пользователя.

## 11. Роли и маршруты

1. Сохраняются роли: владелец, администратор, оператор, исследователь/трейдер и
   пользователь только для чтения.
2. `installation_owner` отдельно владеет восстановлением, доверенными
   настройками и физическими пределами установки.
3. Сервер, а не только интерфейс, проверяет права на Dashboard, Strategies,
   Backtests, Settings и Connections. Целевая матрица:

   | Поверхность | Владелец | Администратор и оператор | Исследователь/трейдер | Только чтение |
   |---|---|---|---|---|
   | Dashboard | Полный доступ в пределах установки | Серверно отфильтрованные операционные данные | Серверно отфильтрованные данные организации и собственных задач | Только разрешённый сервером просмотр |
   | Strategies | Полное управление | Администратор — при делегированном полномочии; оператор — безопасная остановка и сверка состояния | Создание, изменение и выполнение своих стратегий | Только просмотр разрешённых стратегий |
   | Backtests | Полное управление | Администратор — при делегировании; оператор — очередь, отмена и повтор разрешённых задач | Создание, отмена и просмотр своих задач | Только разрешённые завершённые результаты |
   | Settings | Личные, организационные и установочные настройки | Администратор — организация и ресурсы; оператор — просмотр и разрешённые операционные профили | Только личные настройки | Только личные настройки |
   | Connections | Создание, ротация, отключение и архивирование | Администратор управляет жизненным циклом; оператор проверяет, отключает и сверяет состояние без просмотра или ротации секретов | Просмотр готовности и привязка разрешённого подключения к своей стратегии | Только безопасный статус, если разрешено |

   Ограничения, которых ещё нет в серверном API, помечаются
   `target_not_implemented` и не выдаются за действующую защиту.
4. `/models` остаётся канонической защищённой рабочей областью реестра моделей,
   экспериментов, обучения, сравнения, готовности, продвижения и отката в
   разделе исследований. Старый `/strategies?mode=rl_ml` сначала работает как
   совместимый псевдоним, затем получает постоянное перенаправление `308` на
   `/models`.
5. Инструкции являются частью локальной документации. Канонический локальный
   адрес — `/docs/operator/runbooks/{runbook_id}/`. До его реализации старый
   `/runbooks/{runbook_id}` продолжает работать, после чего получает постоянное
   перенаправление `308`. Неизвестная инструкция возвращает `404`; переход
   неавторизованного пользователя сохраняет исходный адрес через параметр
   `next`, а недостаточные права дают `403` или явное состояние ограничения.
6. Операторские инструкции не публикуются на `roehub.com` без явно заданного
   `visibility: public`.

## 12. Документация и `roehub.com`

1. Локальная документация соответствует установленной версии и доступна без
   обязательного доступа в Интернет.
2. `roehub.com` является отдельной публичной поверхностью для описания
   возможностей платформы, документации, истории выпусков, актуального выпуска,
   загрузок и будущей демонстрации. Он не является централизованной Roehub-
   установкой.
3. `roehub.com` и локальная платформа используют общий визуальный язык и
   совместимый клиентский набор технологий, но имеют разные границы доверия,
   учётные записи, авторизацию и развёртывание.
4. Публичный сайт имеет собственную простую учётную запись. Учётная запись
   `roehub.com` не даёт доступа к локальным установкам и не заменяет их
   пользователей, роли или ключи доступа.
5. Сведения о продукте, документация, история выпусков и примечания к выпуску
   доступны без регистрации. Получение ссылки на файл выпуска через
   `roehub.com` требует входа, но исходный код и публичные GitHub Releases не
   скрываются за регистрацией.
6. Окончательные пользовательские статьи, снимки экрана и публичная публикация
   выполняются после стабилизации соответствующего интерфейса.
7. До этого разрешены только структура содержания и минимальная техническая
   оболочка, не выдаваемые за готовую документацию.
8. Один Markdown-источник может собираться для локальной и публичной
   поверхности с версионированием и правилами видимости.
9. GitHub остаётся каноническим открытым каналом исходного кода и выпусков.
   Метрики сайта, GitHub и добровольно зарегистрированных установок считаются
   раздельно и не выдаются за точное число всех пользователей.
10. Архитектура процесса интерфейса и предложенная модель публичного сайта
    уточняются в
    [`roehub-ui-design-and-delivery-architecture-v1.md`](../apps/web/roehub-ui-design-and-delivery-architecture-v1.md)
    и
    [`roehub-public-site-identity-release-and-measurement-v1.md`](roehub-public-site-identity-release-and-measurement-v1.md).

## 13. Не-цели

- централизованная Roehub-установка как обязательная производственная модель;
- зависимость разработки или приёмки от Mac Studio и SSH;
- телефонный интерфейс `390` для локальной платформы;
- переписывание исправной доменной логики только ради нового Web UI;
- обязательное удаление `.npy` как поддерживаемого ускоренного формата;
- ранняя публикация документации со снимками ещё не реализованного интерфейса;
- заранее созданные 13 блоков, этапы, журналы, пакеты промтов, режимы
  `goal_driven` и `manual_sequential`;
- восстановление прежних обязательных дизайн-процессов и их исполнительных
  артефактов;
- общая учётная запись между `roehub.com` и локальными установками;
- обязательная телеметрия или обязательная связь самостоятельно развёрнутой
  установки с `roehub.com`;
- обещание точного числа всех пользователей по регистрации, GitHub-загрузкам
  или добровольной телеметрии;
- представление будущих решений как уже реализованных контрактов.

## 14. Проверка результата

Каждая будущая задача определяет собственную границу доказательств. В
зависимости от изменения это могут быть проверки контрактов, базы данных,
реального браузера, производительности, восстановления, сборки выпуска или
чистой локальной установки. Прохождение тестов само по себе не доказывает
готовность пользовательского результата.
