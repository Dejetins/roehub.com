## 4. Target contracts and ownership

Names introduced in this section are planned symbols, not claims that they exist today. Keep concrete ownership; method naming may be refined with a documented reason without reopening settled behavior.

### 4.1 Source snapshot and deterministic recipe

Add typed `ArtifactCandleSnapshot`, `ArtifactDerivativeBuildRequest`, `ArtifactDerivativeBuildResult`, `ArtifactInputFileReference` and `BacktestPreparedArtifactSet` in the existing artifact contracts module. Add a typed `BacktestInputRecipe` to the existing backtest DTO/domain boundary. Do not put a backtest HTTP request into the artifact builder.

`ArtifactCandleSnapshot` identifies coordinates, source schema and generation, signal/execution timeframes, exact time-axis coverage and origin, price/mapping/funding content hashes and the historical prefix used. The snapshot references published files in place; no per-job copy of all candle arrays. Its files are read-only and protected for the full attempt. Slot identity remains the identity of the real candle source, never a transient bundle alias.

`ArtifactDerivativeBuildRequest` carries explicit candle snapshot, canonical indicator IDs/sources/parameter tuples and row IDs, signal rule/default/compute versions, optional requested TP/SL levels, and trusted output ownership/budgets. It is complete before allocation. Risk `none` requests no hit-time files. Preserve any required indicator dependencies and signal features used by existing selection; do not opportunistically change feature algorithms.

`ArtifactInputFileReference` carries file role, approved source root identity, relative path, content hash, dtype, shape, timeline origin/coverage and applicable row IDs/risk-axis values. It does not accept an HTTP-supplied path. `BacktestPreparedArtifactSet` contains real base references plus derivative references, content/recipe identity and provenance (`reused` or `generated` per component). It becomes consumable only after final validation. Generated files use an actual versioned job manifest, not the publication manifest with invented slot metadata.

`BacktestInputRecipe` uses schema `backtest-input-recipe/v1`: coordinates, requested half-open UTC interval, source-prefix fingerprint and bounds, timeframes, canonical requested rows, rule/default/compute/precision versions, effective funding policy and required funding fingerprint, risk levels and index-domain contract. It is JSON-serializable and durable. It contains no absolute temporary paths. Retention policy, scratch directory, timestamps of generation and reused/generated choice are excluded from financial identity.

Distinguish two phases of source proof explicitly. At preflight/job creation, `source_file_identities` contains the existing published per-file SHA-256, dtype/shape and full original domain from bounded manifest metadata; `prefix_proof` may be `pending`, never a fabricated digest. Preflight does not scan array payloads. During preparation, under the source reservation, verify those original file identities and compute `artifact-prefix-payload/v1` before scoring. The worker emits a prepared-input event; the parent CAS-persists the attestation against the matching job/attempt/recipe and acknowledges it before the child starts scoring. Extend the existing child IPC for this event/acknowledgement, including cancellation, bounded acknowledgement timeout and parent-loss behavior. An unacknowledged attestation cannot start scoring. Completed recipe-aware jobs always have durable verified prefix proof; old schema-1 sources need no immediate full-history backfill.

The prefix proof is distinct from `.npy` file SHA. For each consumed array role, hash a canonical JSON descriptor (sorted keys, compact separators, UTF-8, no timestamp/path) followed by the recorded domain's canonical C-order payload bytes, using a length-prefixed descriptor to avoid ambiguous concatenation. Descriptor fields include schema, role, timeframe, semantic dtype with explicit little-endian byte order, axis order, original UTC origin/end, recorded row count, and shape of that recorded slice. Normalize byte order, not floating-point values or NaN payload bits; preserve the validated numeric policy. Include execution and signal price timestamps/OHLCV, mappings with their original global index origin, and effective funding event timestamps/rates plus the precise original half-open event domain (including required boundary events defined by existing funding policy). Empty funding proof is explicit when applicable; `not_applicable` is not an empty proven funding series. Combine role digests in sorted role order with their descriptors into one source-domain identity. Header bytes, file layout, appended rows and current total shape are excluded. On replay, hash exactly the recorded slices with the original descriptors: appended `.npy` header/shape changes are allowed, any consumed payload change fails. Charge this scan to preparation/hash validation in the benchmark; it must not disappear from timing.

Preserve `request_hash` and `variant_hash` for the same canonical financial inputs. Introduce a separate versioned preparation/recipe identity instead of redefining old `artifact_manifest_hash` as a synthetic value. Extend `BacktestPreflightResult` with the recipe/readiness summary, and preserve `BacktestArtifactMetadata`'s existing published-source meaning. Preserve legacy jobs' hash scheme; version new semantic config identity rather than silently rewriting existing records.

### 4.2 Builder entrypoint and shared computation

Refactor `BacktestArtifactPrecomputeRunnerV2` to expose `materialize_derived(request, source_snapshot, output_directory)` with no canonical-candle-reader dependency for this operation. Keep `export_canonical_price_1m` as the publication-facing operation that obtains canonical candles, writes prices/mappings, invokes the same derivative operation as required by retention policy, and assembles the published manifest. A missing reader is an error at price-export entry, not at construction of a derivative-only builder. No `.npy` implementation of `CanonicalCandleReader` is introduced.

Promote/refactor the existing signal grid/chunk/computation/writer functions under the artifact module's explicit contract. The one implementation must serve scheduled full precompute and job-specific materialization. Reuse `IndicatorCompute`, `GridBuilder`, `signal_rules_engine_v2` and `materialize_hit_times_from_ohlcv_v2`. Do not copy their formulas into the worker. Keep row chunking and memory budgets; no nested process pool or nested Numba workqueue inside an already-owned job child. Publication may retain its existing supported parallel scheduling; the computation contract accepts the existing execution policy.

Compute only required parameter rows and requested TP/SL levels, with their real dependencies. Preserve stable row IDs even when a `.npy` has fewer physical rows than a published matrix. For a partial hit, reuse covered rows/levels and build the missing ones, then expose one coherent logical input set; do not mutate a published matrix in place. Metadata defines the logical-to-physical mapping explicitly.

The initial production implementation preserves the source timeline domain for generated derivatives. SMA/WMA finite windows and EMA recursive seed are computed from the exact same source history as the published baseline. EMA is not restarted at `request.start - max_window`. Do not trim hit-time horizons or rebase sentinels implicitly. Any later timeline truncation needs separate parity proof and is not necessary for this task. Chunk parameter axes when memory requires it; do not split recursive time history without carrying exact state.

### 4.3 Resolution, validation and scoring

Extend existing `BacktestPreparePoolsService` with `prepare_artifact_inputs` (planned), which resolves the typed recipe against the available published inventory and asks the existing builder for missing derivatives. It returns `BacktestPreparedArtifactSet`; `open_artifact_arrays` consumes this set through the evolved `BacktestArtifactArrayLoader`. The application service must not resolve physical paths itself or import private filesystem writer functions.

`FilesystemBacktestArtifactArrayLoader` uses each trusted explicit reference rather than recomputing all paths from a single slot. Reuse its `np.load(mmap_mode="r", allow_pickle=False)` path and strict dtype/shape checks. Path validation must constrain references to the pinned base root and the owned attempt root, reject traversal/symlink escapes and distinguish absent optional data from corrupt/incompatible data. A bad checksum or invalid present file fails closed; it is not hidden by silently computing a replacement. Unsupported math versions fail explicitly.

The new root publication schema is version 2; version 1 remains strict and readable. In version 2, prices/mappings and required funding remain explicit; signal inventory may be empty/partial and hit-times may be absent. `validate_slot` validates what publication policy promises and every declared file. Add `validate_prepared_inputs` on the existing validator for the complete run request. The generated job manifest has its own kind/version and never passes through slot validation by pretending to be a publication.

`BacktestRuntimeJobOrchestrationService.execute` prepares once per attempt before scoring and shares the ready set with request slicing, sample warmup and TP/SL loading. `BacktestTpSlHitTimesService.execute/validate_grid/materialize_subset` reads selected generated/reused tables with exact grid values and index semantics. Financial kernels (`no_risk_exact`, `tp_sl_exact`, matrix scoring, ranking/tie rules, sizing/funding calculations) retain their current algorithm and precision.

### 4.4 Job lifecycle, resources and concurrency

Extend the existing parent-owned child temporary directory to contain `inputs/`; pass its trusted location through internal child arguments/config, never the public request. Both full-job and lazy-detail parents own attempt directories. Each retry gets a new attempt identity. Writes go to private incomplete files; final manifest/ready state is committed atomically only after required files are closed and validated. Never change `current.yaml` during a backtest.

The parent closes/reaps the child before directory cleanup. `finally` cleanup handles success, exception, cancellation and timeout. Worker startup/periodic recovery removes orphan attempts only after checking the existing job/materialization lease and child ownership, not merely file age or reusable PID. Retain no open mmaps into files selected for cleanup. `BacktestJobScratch.clear` continues releasing array references; explicit file ownership remains with the process lifecycle rather than an unrelated global cleanup helper.

Enforce finite admission estimates for generated bytes and peak compute memory before allocation. Add runtime-config bounds for per-attempt generated bytes and total worker scratch, with a free-space reserve. Conservative engineering defaults for the new profile: 2 GiB generated files per attempt, 8 GiB worker scratch and 1 GiB free-space reserve; validate them against current worker memory/concurrency limits before enabling and document any evidence-based adjustment. These are disk guards, not permission to allocate 2 GiB RAM. Existing stricter memory/chunk/cell budgets win. Native reused files do not consume the transient disk allowance, but their mmap/working memory still counts. Avoid sum-of-estimates races: reserve capacity at the existing worker admission boundary before launch and release after cleanup; do not add a separate scheduling service.

Queued/running jobs retain their actual candle slot pin. The present `count_active_for_artifact_manifest` is a separate SELECT and `PsycopgBacktestPostgresGateway` opens a new connection per call; a common transaction/ownership guarantee does not exist today. Extend these existing owners explicitly, without adding a new adapter or external service:

- Add `BacktestPostgresGateway.transaction()` with operations bound to one connection for the transaction. Add migration tables `backtest_artifact_slot_ownership` (one row per normalized physical exchange/market/symbol/slot) and `backtest_artifact_slot_readers` (owner kind, organization/job or lazy-request ID, attempt, parent incarnation, expected generation/manifest, state). Generation is validated data, not part of the mutex key: old and new generations at the same path must exclude one another. Ownership information is internal, never an API inventory of another organization.
- Add explicit repository operations `reserve_artifact_reader`, `release_artifact_reader`, `reserve_artifact_writer`, `complete_artifact_writer` and quarantine/recovery transitions. Each locks the same ownership row with `SELECT ... FOR UPDATE`. A reader can register only when no writer/quarantine exists and its expected generation matches; a writer reserves only when no reader exists, including queued jobs and active lazy operations. Writer reservation carries an unguessable owner token and monotonically increasing epoch. Mutations require exact owner/attempt/epoch predicates.
- Job creation acquires the reader reservation and persists the queued job/recipe in the same database transaction after revalidating the selected slot metadata under ownership. Read-only preflight creates no reservation. A changed source is a typed stale-preflight outcome, not silent recipe replacement. Worker claim transfers queued ownership to its attempt by CAS. Lazy replay reserves the compatible candidate slot before prefix hashing/mmap. Release follows completion/cancellation and confirmed child reap, never merely an expired heartbeat.
- Publication reserves writer ownership before rebuilding the inactive slot. Build in a private staging directory; never mutate existing published files with `r+` while computing the candidate. Recheck owner/epoch and validate the candidate before the short finalization section, then atomically install ready files/manifest and switch the pointer under exclusive ownership. No new readers are admitted until the generation transition completes. The publisher's previous-slot cleanup path also requires writer ownership before deletion; it cannot use its current check-then-delete sequence. Include the corresponding use-case and CLI cleanup entrypoints in the caller migration.
- Publisher reservation locks both slot-ownership rows for the coordinate in a deterministic order and permits only one publication/destructive-cleanup writer across that coordinate. Under that reservation, reread and compare the expected `current.yaml` identity and target generation: a stale precheck is rejected before filesystem mutation, and an active slot cannot be treated as inactive. Register a reader reservation on the incremental reuse source in the same transaction and hold it for all source reads. Immediately before the pointer switch, compare the original pointer identity again under the same coordinate writer ownership; a mismatch fails without switching. Cleanup similarly revalidates that its target is not current. Two publishers with stale prechecks must never rebuild/delete a now-active target or read an unprotected incremental source.
- A lost job/publisher lease, DB session failure, or uncertain owner state quarantines its reservation; it does not make live files reclaimable. Keep durable reservations until the supervising process has terminated/reaped the exact child or recovery proves the owner incarnation is dead. Epochs fence DB commits, but are not claimed to fence filesystem writes by themselves. Never hand a writer slot to a successor merely because TTL expired while an old writer may still write. Recovery with insufficient liveness evidence fails closed and reports the owning attempt for operational repair. After confirmed writer death, validate/reconcile the pointer and staged/final manifest before clearing quarantine; preserve a valid published generation and discard only owned incomplete staging.

This protocol covers admission after preflight, ordinary execution, lazy replay, inactive-slot rebuild and previous-slot deletion. Implement it within existing gateway/repository/publisher/process owners, with no generic locking framework. Test forced interleavings and DB/owner loss with real Postgres. Reservations are execution lifetime protection, not permanent retention of every derivative version.

No cross-job transient derivative cache is required in this implementation. It would add cache eviction/lease complexity and undermine clear disk ownership. Persistent precomputation remains the supported reuse mechanism. Attempt files are deleted at completion; constant storage grows only according to explicit instrument policy.

### 4.5 Persistence, replay and lazy details

Add nullable versioned recipe/provenance columns to jobs, and the corresponding lazy request/cache identity where necessary, through a new ordered SQL migration plus `migrations/postgres/manifest.json`. Select the next free migration number at implementation time; do not edit an existing applied migration. Keep the existing slot pin as the real base source. New jobs carry recipe version 1; missing recipe means the tested legacy behavior, not guessed provenance. Update entity construction, repository mapping, job creation/read DTOs and worker serialization together.

`BacktestJobWorkerUseCase.run_next` may revalidate admission, but must execute stored financial request/config/recipe semantics. Revalidation must not silently overwrite the recipe with today's defaults or current pointer. Add an explicit stored-recipe validation path in `BacktestPreflightService`, preserving source identity and treating incompatible source/history/version as a typed failure.

Persist preparation provenance before discarding transient files, with compare-and-set on job lease/attempt ownership. Stale workers must not overwrite another attempt's provenance or result. A failure before a ready set does not write fictitious file hashes. Round-trip all existing funding metadata through `child_ipc.py`; add regression coverage for fields currently reconstructed manually.

`BacktestLazyTradesDetailService._recompute_payload` reconstructs a selected variant from the saved recipe, only its rows and selected TP/SL pair. After slot turnover it may use a newer published snapshot only when the entire originally consumed prefix/time-domain/funding fingerprint and computation versions match. Slice to the recorded original domain before rebuilding, so appended future bars cannot change hit-time sentinels or final-bar semantics. If proof fails, return a stable explicit source/version-unavailable error; never substitute current data and claim exact replay. Legacy jobs continue their established path and limits. No promise of replay after arbitrary history corrections is added.

Keep lazy cache keys organization-scoped and versioned by the semantic recipe/selected variant. Retention changes or a temporary directory rename do not invalidate identical financial results; source/rule/funding changes do. Check result candles/series/CSV consumers as well as trades. API payloads expose bounded readiness and provenance only, never local paths or raw manifests.

### 4.6 Storage policy and API behavior

Extend `BacktestArtifactsRuntimeConfig` with versioned per-coordinate overrides (exchange, market type, symbol) for `signals: precompute | on_demand` and `hit_times: precompute | on_demand`; existing signal target selections continue defining which indicators to precompute. New on-demand computations remain bounded by supported indicator definitions and configured allowable risk levels, independent of stored coverage. Candles/mappings stay published; funding follows the existing effective policy.

For existing configurations, omitted policy means current precompute behavior. A new explicitly selected storage-efficient profile can use on-demand derivatives; do not change every installation default or delete its old files during a rollout. Existing valid derivatives may still be reused under on-demand policy; that policy stops proactive retention/building on subsequent publication, not correctness-preserving reuse. Switching back to precompute builds missing derivatives through the same builder. Policy never changes already queued job semantics.

Update `to_precompute_runtime_settings`, `to_validation_spec`, config loading/hash functions, publisher use case, scheduler/CLI wiring and installation config generation. Split semantic calculation configuration from retention/execution-storage configuration; version the split and preserve legacy identity. Generated installation configs must be regenerated through their existing generator, not patched independently.

`POST /backtests/preflight` remains a cheap validation/read operation: no indicators calculated and no derivative writes. Extend its typed response with safe `input_readiness` (`ready` or `requires_materialization`), component counts and bounded estimates. Missing/corrupt candles still fail; a missing derivative with a supported recipe succeeds with materialization readiness. Job creation remains idempotent under existing organization/request rules. Normal requests need no new strategy parameter or compute-mode switch.

## 5. Compatibility and rollout

These are target assessments, conditional on the specified tests. They do not claim deployed compatibility.

| Boundary / consumer | Before -> target | Classification and required evidence |
| --- | --- | --- |
| Existing financial request and top-result contracts | Same canonical financial request, ranking, variants and metrics | `none` intended; exact identity/order and existing metric tolerance tests required. |
| Existing API clients -> new server | Existing fields retained; additive readiness; optional derivatives no longer force unavailable | `compatible-change` for inspected clients, conditional on DTO/client tests and unchanged error shape. Unknown external strict consumers remain `unknown`. |
| New reader -> old root manifests/jobs | Strict schema-1 read; nullable recipe -> legacy execution | `compatible-change`; fixture and old-queue replay tests required. |
| Old reader -> schema-2 partial roots / new prepared manifest | Old exact version/key parser cannot read them | `breaking-change`; readers must precede writers, old workers must drain before new jobs/schema are enabled. |
| Existing artifact array port / internal context | Slot-only -> explicit prepared input references | `breaking-change` internal call contract; update all direct callers/wiring/tests in the staged change, no compatibility adapter. |
| Postgres old rows -> new reader | Add nullable recipe/provenance; old rows unchanged | `compatible-change` conditional on real migration/repository proof. Old worker handling new rows is unsupported and must be prevented by rollout ordering. |
| Existing config -> new reader | Omitted policy preserves existing publication | `compatible-change`; strict parser/default/hash tests. Old parser -> new policy keys is `breaking-change`. |
| Cache and semantic hashes | Legacy unchanged; new identity excludes storage-only choices | `compatible-change` only with explicit recipe/version namespace. Silent in-place reinterpretation would be `breaking-change` and is forbidden. |
| Operations and filesystem | Job preparation adds temporary writes, disk admission and orphan recovery | `compatible-change` with explicit bounded budgets, ownership and cleanup proof; not a performance win claim. |

Rollout order: (1) additive DB schema and readers that understand old/new data, with old writing/defaults preserved; (2) worker/builder/loader/lazy full path and local proof; (3) drain incompatible workers/queues and upgrade every publisher/previous-slot cleanup process in an explicitly selected installation; (4) enable shared slot ownership, schema-2/recipe-aware writes and per-instrument policy only when all participants honor the protocol; (5) verify before any retirement of derivatives. Old COUNT-only publishers cannot coexist safely with new lazy-reader reservations. This pack performs local disposable rehearsals only, not production rollout.

Rollback before new writes can return to old code without data conversion. After schema-2 partial publication/new jobs exist, old code is not a safe rollback. Keep new readers, stop new submissions/policy changes, drain or retain new jobs, and rebuild complete compatible artifacts before a separately authorized old-binary rollback. Do not drop new provenance columns or destroy old evidence. Existing artifact deletion is not part of automatic migration. No irreversible transformation is planned.
