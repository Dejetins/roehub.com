## Class inventory and security/lifecycle contract

| Class | Participating clients | Query / aggregate MiB | Concurrent / threads |
|---|---|---:|---:|
| stream | collector composition, one-shot/recovery children, persistent writer, strategy live runner | 128 / 192 | 2 / 2 |
| interactive | API reference/catalog/history/coverage wiring and dashboard reads | 128 / 192 | 4 / 2 |
| backfill | scheduler normal/request paths, CLI catchup and writer factory | 128 / 128 | 1 / 1 |
| artifacts | publisher composition and artifact-publish CLI, S01 indexed discovery and native source/funding reads | 128 / 128 | 1 / 1 |

`client-inventory-01.txt` records call sites. Shared/pool/child clients inherit the
class from composition; HTTP parameters do not select it. Bounds aggregate across
processes/replicas using the same user on **one ClickHouse server**. They do not
span multiple servers and do not reserve CPU/IO or charge all background merges
to a foreground user. Global capacity and default legacy settings are preserved.
All classes have cooperative 30-second execution limits; ordinary clients cannot
raise/unset caps or select `default`. `async_insert=0` and
`wait_for_async_insert=1` are locked, keeping MV writes in synchronous accounting.

Grants cover actual candle raw→canonical→stats, reference/funding/absence paths.
Interactive/artifacts are read-only. Stream cannot mutate reference data.
Administrative migrations, bounded local health checks, catalog/funding admin
CLIs and diagnostics remain explicit exclusions; workload-required mode refuses
an unclassified admin command rather than silently choosing an unrestricted user.

`legacy` → `provisioned` → `active` is opt-in. `provisioned` keeps additive users
while legacy apps continue; rollback drains apps and restores that mode/image,
retaining users/passwords/data. Fresh private files are 0600 in 0700 directories;
existing credentials are reused byte-for-byte, conflicts/symlinks fail closed.
Apps mount only their class file and clear generic credentials. The generated
bootstrap installs hash XML as `600:clickhouse:clickhouse`, then invokes the
image entrypoint. Remote `default` is denied. Remote-default installations must
first complete a separately authorized identity migration; an admin account alone
is insufficient to preserve their app access. Runtime UID/file readability is a
preflight requirement, not a reason to broaden permissions.

`recreate-03.json` proves generated ClickHouse service recreation through
`legacy → provisioned → active → provisioned`, unchanged passwords/admin access,
all class settings, denied remote default, successful MV writes and retained
canonical/bitmap counts. Application env/mount switching is unit-tested, not an
installed application upgrade. No credential rotation/account removal occurred.

## Frozen mixed-load protocol and all results

`tools/qa/market_data_mixed_load.py` extends
`market-data-resource-comparison/v1`; `mixed-workload-frozen-02.json` binds exact
harness/loader/profiles/grants/classifier bytes and declared order
**B1,C1,C2,B2,B3,C3**. The baseline dynamically loads snapshot client wiring and
accepted S01 readers; candidate uses current class identities. API route/reader
source is otherwise unchanged. Every run has a fresh disposable database, four
contiguous 2,880-minute streams and 98 sparse coordinates (every seventh minute
missing), fixed UTC cutoff and identical data generation. Existing server caches
are not cleared; every run warms for 60 seconds then measures 300 seconds.
Same server is reused, so allocator/cache/merge and shared-host noise remain.

Offered lanes are 1/s four-candle live batches, 2/s actual catalog ASGI responses,
two separate backfill processes at 1/s each, and two separate artifacts processes
at 1/s each. Backfill performs the same 16-pass verification checksum plus
1,440-minute raw/MV write. Artifact work uses S01 discovery plus actual canonical
reads. Simultaneous low-priority bursts saturate class admission; this is not a
claim of continuous full-CPU saturation or a capacity envelope. Retry is bounded
at 30 attempts and finite work drains with a 600-second deadline; no offered work
is dropped or excluded after a failure.

Live latency is **offered batch → acknowledgement of all four synchronous MV
writes**, not exchange receive/PG receipt latency. API is the actual production
route/ASGI serialization and CH coverage reader with fixed auth/catalog/PG
projections, not installed HTTP/network/auth/PG performance. Each quantile uses
operations offered in `[60,360)` (300 live batches / 600 API reads per run), linear
interpolation. The table reports every pair; aggregation uses median of the three

### Regression investigation and resolution

Live p95 improves in all three pairs (median −50.2%). Live p99 median is **+14.6%**,
with baseline range **97.72–280.22 ms**, candidate **49.61–133.76 ms**, paired deltas
**−58.17 / −156.70 / +36.04 ms**. Its direction is **inconclusive**; the regression
is not declared disproved. `tail-investigation-01.json` shows all live operations
succeed on attempt 1, queue wait at most 5.93 ms, and service-time spikes on both
sides. Cgroup throttled periods fall from 360/409/415 to 13/28/49; this supports
lower burst CPU pressure but does not establish the cause of individual subsecond
spikes. Sampling cannot isolate those causes.

API median p99 improves, but the first pair regresses 4.99 ms. Auxiliary
`api-only-ablation-01.json` runs three alternating API-only closed-loop pairs,
50 warmup + 300 measured requests each: baseline p99 16.93–19.55 ms, candidate
17.33–18.29 ms. This does not show a stable intrinsic API identity penalty and
**does not explain stream p99** or replace the fixed offered-load experiment.

Resolution: retain the measured p99 regression/uncertainty, make no universal tail
latency/SLO claim, and accept only the measured resource isolation and correctness
within D2. Memory/concurrency controls are not CPU/IO reservations. All finite work
and safety checks pass; no numerical target was specified. Independent follow-up
review agrees that this bounded investigation/resolution meets M before stage
advancement; it does not establish numerical performance or release readiness.
