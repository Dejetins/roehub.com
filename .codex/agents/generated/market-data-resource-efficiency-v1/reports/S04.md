# S04 — Asynchronous batched durable stream recovery

## Outcome and scope

D4 is implemented and tested locally. Required M1 contains exactly three paired
baseline/candidate repetitions at each of four and 100 streams (12 successful
runs). All offered candles reached canonical storage with exact key/OHLCV parity;
all journals drained. Event-loop p99 and PG transactions/candle improve at both
scales. Four-stream ACK latency worsens modestly, and 100-stream prompt writes
produce more CH queries/parts than the stalled baseline. This is not a universal
resource or latency improvement.

`performance_acceptance: not assessed — numerical threshold not specified`

Executor: `s04-20261011-async-recovery`. Only S04 executed. The atomic updater owns
acceptance/completion; this report is not an execution-state substitute. No fifth
stage, publication, branch/worktree/stash/Goal, staging, commit, installed activation,
credential change to installed services, data reset or resource-limit increase.
Installed runtime remains pre-S01. Its observed live progress is not S04 rollout.

## Source, ownership and implementation

`baseline-source-01.json` preserves 1,594 files before behavior changes at

`owned-paths-01.json` lists 13 owned source/test/canonical-doc paths; generated map

`candidate-freeze-01.json` binds 1,598 files at
`.cache/market-data-s04-candidate-20261011`; the frozen harness ran on both sources.
`source-final-03.json` verifies baseline/frozen snapshot integrity and final owned
hashes. One post-measurement harness edit wraps an overlong SQL string for Ruff;
AST equality is proven, measured frozen bytes retained. No production/config or
workload behavior changed after freeze, so no cosmetic remeasurement was run.

- Additive `AsyncStreamRecoveryStore` port and native async PG adapter retain the
  existing journal schema, recovery keys and conditional token predicates. One
  lifecycle-owned session holds both collector lease and every recovery/health
  transaction. No connection-per-candle; no shared session concurrent commands.
- Application coalescer owns bounded batches (256 rows, 2 ms), reserving metadata
  capacity including in-flight work. Buffer reserves before persistence, returns
  acceptance after commit, then uses the existing warmed killable writer and
  token-fenced completion. REST enqueue reserves without holding Condition over PG.
- Waiting-before-persistence is cancellable; repeated caller cancellation cannot
  cancel shared commit. Already committed work remains buffer-owned or durable
  for restart. Closing the PG socket precedes timeout cancellation, because the
  ordinary async timeout was experimentally shown to hang on a blackholed reply.
  A poisoned lifecycle cannot publish/acknowledge; restart reacquires the lease and
  reconciles exact keys, returning existing tokens after an unknown commit.
- `pending`, failed-history reads, retry/fail/advance/completion and connection
  health are async in collector wiring. The remaining synchronous history cleanup
  runs in managed preparation I/O/fallback off-loop reading. S03 HTTP pool,
  provider permit fencing and persistent writer implementation are unchanged.
- Total buffer-owned rows include waiting producers/admissions/buffer/retries:
  `2 * max_buffer_rows`, with at most `max_buffer_rows` admitted to persistence/write.
  Accounted-byte reservation is capped at 64 MiB; it is a conservative object and
  bookkeeping estimate, not exact heap/RSS. Coalescer metadata has its own 20,000
  task cap and bounded strings. Excess work is unaccepted and covered by reconnect/
  tail recovery. No claim of exactly-once delivery across PG and CH.

## Frozen method and runtime

`M-protocol-frozen-01.json` contains every exact command. For each scale order is
B1,C1,C2,B2,B3,C3. The injector supplies private disposable settings without
printing/storing their values. Final experiment is a **finite accelerated replay**:
102 sparse/contiguous stored coordinates, 2,880-minute seed; three identical warmup
bursts, then 60 synchronized bursts on an absolute 0.2-second schedule, buffer1000,
flush100ms, full completion and five-second post-drain observation. Four streams
supply240 candles;100 streams supply6000. It is not a service steady-state workload,
so no 60s/300s service-window claim is made. Delayed baseline dispatch is visible
in scheduled→ACK separately from receive→ACK; workload is not silently rescheduled.

`runtime-identity-01.json` and `runtime-config-binding-01.json` record host/runtime,
image/config hashes and unchanged limits. macOS ARM,18 logical CPUs,38,654,705,664
bytes,Python3.12.12; PG16.15 at512MiB/1CPU; CH25.8.33.6 at1.5GiB/2CPU with1GiB
server budget. Same S02 stream identity/profile and one warmed writer on both sides.
S02 enforced `async_insert=0`/`wait_for_async_insert=1` make ACK follow synchronous
raw+MV execution; exact final canonical content is independently read and compared.
Latency is explicitly writer-ACK timing, not a per-candle visibility timestamp or
public API/provider latency.

PG stats use a new isolated database per run; sampling connections use `postgres`,
so their transactions do not contaminate workload DB counts. Existing warmed
sessions are outside the sessions-created delta: candidate0 means no new session
during measured work, not zero total sessions (sampled candidate peak1). Background
DB maintenance can contribute to raw totals. RSS is parent+writer summed at the
same sample, excluding Docker/ps helper processes; CPU is parent+live-child deltas.
CH tracked/allocator/RSS/cgroup,PG cgroup,CPU/IO,parts/merges remain separate in raw
reports. One-second sampling misses shorter peaks; five-second post-drain is not
leak exclusion. Legacy total-retained counters did not exist: baseline raw zeros
and their derived bound booleans are **N/A for total-intake bound proof**. Actual
legacy buffer length is sampled; candidate bounds have real counters plus tests.

### Direction, regressions and M.7 resolution

Loop and PG improvements at both scales and 100-stream ACK/completion improvements
exceed observed three-run spread. Four-stream total completion is cadence-bound;
its ~0.3% change is not a meaningful throughput claim. RSS is effectively unchanged
at four streams and ~2.8% lower at100; these short runs do not establish a general
memory reduction. No overall initial-to-final speedup is computed across unlike
stage workloads.

Four-stream receive→ACK p99 medians123.15→127.75ms (+3.74%); receipt→ACK
110.73→117.95ms (+6.52%). Candidate receive p99 values125.20,127.75,150.01ms
are retained, including the worse third run. Scheduled→ACK median128.47→128.72ms
(+0.20%) has overlapping ranges; this does not erase the receipt/receive regression.
The additional2ms coalescing and changed admission/write scheduling are a structural
latency tradeoff; they do not explain every tail sample. Bounded read-only
`M1-four-stream-tail-diagnostic-01.json` shows equal60 INSERT+60 Describe calls/run,
INSERT median4ms on both sides, server INSERT p99 baseline7–10ms/candidate10ms.
Thus a large CH server INSERT slowdown is not demonstrated; exact process/client/
admission contribution to the150ms observation remains uninstrumented. No fixture
had loss, growing final backlog or incomplete drain. Retaining this small-workload
tail cost in exchange for lower loop stalls/PG work and the100-stream behavior is
the reasoned local resolution, not an invented SLO pass or claim of all-tail improvement.

Four-stream CH cgroup CPU rises in this short fixture; preserve the measured table
rather than calling total infrastructure CPU lower. At100 streams, baseline stalled
into13 large INSERTs whereas candidate makes60 timely INSERTs (26→120 CH QueryFinish,
including Describe); sampled parts33→37. This is the cost of prompt bounded writes,
not a batching-count improvement. No persistent parts accumulation or long-run
compaction-capacity claim follows from this short observation. PG and client CPU
fall substantially within this recovery-only fixture. S03 provider-quota overhead
is outside this path and remains an explicit unresolved capacity cost for rollout.
