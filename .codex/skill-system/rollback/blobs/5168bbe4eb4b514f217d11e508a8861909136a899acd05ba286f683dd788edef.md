# Global Agent Baseline

## Precedence
- Repository-specific instructions override global rules.
- Follow project docs, repository instructions, hooks, rules, and existing code patterns before personal preference.
- If instructions conflict, follow the highest-priority applicable instruction and state the conflict when it materially affects the work.

## Repository Instructions
- Before task actions, read applicable repository instructions such as `AGENTS.md` and repo-local Codex guidance when present.
- Treat repository instructions, hooks, rules, and skills as the source of project-specific workflow policy.
- Do not infer repository-specific workflow from old chats, stale plans, branch names, folder names, or historical conventions when current repo guidance says otherwise.

## Change Discipline
- Make minimal diffs.
- Avoid broad refactors unless requested.
- Preserve existing conventions where practical.
- Keep edits scoped to the requested behavior and directly related documentation.

## Git Discipline
- Do not create branches, worktrees, stashes, temporary checkouts, auxiliary local folders, or extra workflow files unless the user explicitly asks for that workflow.
- If the current Git state is unsafe, dirty, mixed, or ambiguous, report the blocker or stage only explicitly scoped files; do not create parallel folders as a workaround.
- Never stage unrelated changes silently.
- Do not use destructive Git commands unless explicitly requested and narrowly scoped.

## Safety
- Do not silently change contracts or externally visible behavior.
- Do not leak secrets, tokens, cookies, credentials, raw provider payloads, or sensitive data.
- Do not add dependencies unless justified.
- Do not swallow errors or hide failed checks.

## Contract Classification
- For non-trivial compatibility analysis, classify affected dimensions as `none`, `compatible-change`, `breaking-change`, or `unknown`.
- Use a simple yes/no only for trivial work where the contract dimension is clearly unaffected.
- State rollout, migration, or backward-compatibility risks when relevant.

## Execution
- State assumptions explicitly.
- Run relevant checks when available.
- If checks or tests were not run, say so.
- Distinguish implemented facts from proposals, inference, and unverified assumptions.
- Prefer focused investigation and focused verification before broad repository-wide commands.

## Validation Depth
- For non-trivial changes, tests are a gate, not acceptance by themselves.
- Use the nearest meaningful real-boundary evidence when relevant: API, database, browser, runtime, CI/deploy, benchmark, integration smoke, or target-environment proof.
- Tests-only acceptance is acceptable only for trivial internal changes with no public contract, persistence, browser-visible, runtime, ops, performance, or delivery impact.
- For performance claims, require baseline, comparable measurement method, and evidence.

## Default Python Gates
- For Python repositories, prefer project wrappers and uv-based commands when available:
  - `uv run ruff check <target-or-.>`
  - `uv run pyright`
  - `uv run pytest -q <target-or-empty>`
- Use focused targets first, then broaden only when risk, failing evidence, or repository policy requires it.
- If a repository is not uv-based or exposes a stronger wrapper, use that repository's wrapper instead of forcing these commands.

## Artifact Review
- For architecture docs, plans, prompt packs, prompt files, agent instructions, or skill-routing changes, perform one cold independent review when available and allowed by the environment.
- If an independent review is unavailable, perform a cold self-review fallback and label it clearly.
- Do not report such artifacts as ready/final without stating review mode, verdict, fixed blockers, follow-up check, and residual risks.

## Skill Routing
- Use skills as compact procedural helpers, not as a reason to preload broad context.
- Bug fixes, regressions, failing tests, stack traces, or "worked before" reports → `root-cause-debugging`.
- Diff, branch, or PR review focused on production risk → `production-risk-review`.
- Browser-visible QA, screenshots, console/network checks, and real user-flow verification → `browser-qa-evidence` with the available browser tool.
- Ship readiness, PR handoff, release evidence, and docs drift checks before publishing → `pre-ship-gate`.
- Architecture review, review-first refactor analysis, plan assessment, docs/code drift, and docs-sync → `architecture-review`.
- New architecture, target-state design, bounded-context design, dependency direction, ports/adapters, service boundaries, module structure, data flow, integration contracts, service integration design, ADR drafting, platform evolution, boundary reshaping, and phased migration design → `architecture-design`.
- Contract compatibility analysis → `contract-impact-analysis`.
- Backend gates → `backend-quality-gates`.
- Backend performance evidence → `backend-performance-evidence`.

## Reporting
- Mention residual risks or follow-up work when relevant.
- Summarize what changed, what was verified, and what was not verified.
- Keep final reports concise, factual, and scoped to the user’s request.
