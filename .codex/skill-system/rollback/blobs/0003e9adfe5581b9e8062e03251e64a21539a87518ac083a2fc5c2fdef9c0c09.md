# Data Analytics Methodology

Use this skill when the task is not only to manipulate data, but to frame a business problem, choose an analytical approach, define direct or proxy metrics, test a business hypothesis, compare groups over time, evaluate customer/channel economics, or write a business conclusion.

This skill complements project `AGENTS.md`: `AGENTS.md` controls workspace execution, notebook structure, data loading, joins, exports, and formatting. This skill controls analytical thinking, method choice, evidence quality, and claim strength.

For `/Users/daniildegtyarev/Yandex.Disk.localized`, all user-facing methodology plans, explanations, chart/table interpretations, notebook Markdown, report text, and final conclusions must use Russian as the primary language unless the user explicitly asks otherwise. English is allowed only for exact technical identifiers, field names, formulas, code/API/library names, canonical abbreviations, or method names that need exact wording. Do not produce bilingual slash labels, hybrid Russian/English phrases, or English filler inside Russian text; use Russian wording with the exact English token in backticks or parentheses only when needed.

When a selected methodology requires large transformations, feature creation, repeated metric calculations, or heavy aggregations, prefer calculation designs that can be implemented with vectorized NumPy/pandas operations. Avoid method plans that require row-wise Python logic on large tables unless there is no defensible vectorized alternative.

For complex calculations, the methodology plan or notebook comments must name the selected algorithm, expected row/group scale, Big O / memory complexity, and why the method is preferable. If the calculation risks cross joins, repeated scans, or slow grouping, address that risk before implementation.

## Routing Algorithm

Apply methods in this order. Do not skip earlier steps when their condition applies.

1. Identify the user question, requested decision, expected output, and available source data.
2. Classify analysis depth.
3. If the task is complex, load `business_problem_framing` before choosing calculation methods.
4. If data is new, external, unfamiliar, recently refreshed, or suspicious, load `data_quality_audit` before any analytical method, then use `data_quality_verification` before strong conclusions.
5. If this is the first analytical pass over a source or the correct method is not yet obvious, load `exploratory_data_analysis` after data-quality checks.
6. If the task needs historical context, long-term dynamics, seasonality, or structural-shift context, load `business_dynamics_context`.
7. If the metric is not canonical or the denominator/numerator/grain is ambiguous, load `metric_design` before calculations. If the metric should become reusable, feed a forecast, support a management decision, or move toward `verified`/`canonical`, also load `metric_certification`.
8. If direct measurement is unavailable or imperfect, load `proxy_metric_design` before calculations.
9. If missing values affect joins, denominators, metric calculation, model features, or conclusions, load `missing_data_imputation` before final calculations.
10. If derived features are created for ML, clustering, uplift, forecasting, anomaly detection, matching, or repeated reuse, load `feature_engineering` before modeling or interpretation.
11. Choose the primary domain method:
   - client lifecycle over time -> `cohort_analysis`;
   - channel/store movement -> `channel_migration_analysis`;
   - campaign, promo, bonus, or loyalty mechanic -> `campaign_effect_analysis`;
   - migration economics -> `channel_migration_economics`;
   - price, volume, and mix effects -> `price_volume_mix_decomposition`;
   - trend, seasonality, or spike/drop -> `time_series_anomaly_analysis`;
   - segment contribution or rule-based segmentation -> `segment_rfm_abc_analysis`;
   - hidden behavioral groups -> `clustering_segmentation_ml`;
   - prediction/propensity -> `predictive_modeling`;
   - incremental targeting -> `uplift_modeling`;
   - future values -> `forecasting` plus `forecast_backtesting_protocol`; add `catboost_forecasting` when using CatBoost, direct multi-horizon tabular ML, panel segments, residual correction, quantile intervals, scenarios, ensembles, or hierarchy reconciliation; add `sarima_forecasting` when seasonal ARIMA/SARIMA/SARIMAX, stable recurring seasonality, or known future regressors are part of the candidate method;
   - unusual entities or points -> `anomaly_detection_ml`;
   - co-purchase or recommendations -> `basket_affinity_analysis`.
12. If the task explicitly asks for Mapper, persistent homology, topology-derived features, time-delay embedding, structural topology, embedding topology, or topology balance, use companion skill `topological-data-analysis` and keep the result framed as structural diagnostics unless another method validates the business claim.
13. If the task asks whether something affected, caused, changed, or increased another thing, load `hypothesis_analysis`.
14. If the task needs causal language, incremental effect, or a counterfactual, load `causal_inference`; if no credible causal design exists, downgrade to descriptive language and state the limitation.
15. If the task asks whether a difference is reliable, significant, or likely noise, load `statistical_inference`.
16. If there is any randomized experiment or holdout, load `experiment_ab_testing`.
17. If any ML model is used, load `model_validation_guardrails` before model interpretation.
18. If a model, forecast, score, segment, or metric will be reused after the notebook, load `model_monitoring_and_drift` and define monitoring/retrain triggers.
19. Before calculations for `глубокое исследование`, present the methodology plan and wait for approval.
20. Before final charts, final reader-facing tables, executive summary, or business conclusion, load `chart_and_conclusion_review`.

If two materially different routes are plausible and would lead to different calculations or conclusions, ask the user before implementing. If one route is a conservative default and the risk is low, state the assumption and proceed.

## Clarification Policy

Ask the user clarifying questions when the missing decision materially changes the method or conclusion. For `глубокое исследование`, do not under-ask: it is acceptable to ask many focused questions when they change the population, method, metric, evidence strength, or business interpretation.

Ask when any of these are missing and cannot be safely inferred:

- target outcome metric;
- treatment/event date or period;
- unit of analysis: client, order, SKU row, store, day, month;
- comparison group or baseline period;
- inclusion/exclusion rules that change population;
- output format or required business cut;
- whether the user wants causal language or descriptive evidence only;
- for ML tasks: target event, prediction point in time, feature availability date, acceptable false-positive/false-negative tradeoff, and intended business action.

Do not ask when the workspace catalog, table docs, user prompt, or a conservative default is enough. State the assumption in the notebook and proceed.

If a decision fork exists, present the fork plainly:

```text
Decision needed:
- Option A: ...
- Option B: ...
Why it matters:
Recommended default:
```

## Must Ask User If Missing

Ask the user before calculations when a missing item would change the method, population, metric, or conclusion and cannot be safely inferred:

- outcome metric or business KPI;
- unit of analysis: client, order, SKU row, store, day, month, campaign exposure, or basket;
- analysis period, treatment date, event date, or forecast horizon;
- comparison group, control group, baseline period, or counterfactual;
- inclusion/exclusion rules for clients, channels, promo rows, staff, corporate clients, returns, or incomplete periods;
- whether the user wants causal proof, directional evidence, or descriptive profiling;
- for statistical inference: compared groups, independence/paired structure, and minimum practical effect if the conclusion depends on "no meaningful effect";
- for ML: target event, prediction/scoring date, feature availability date, label window, intended action, and acceptable error tradeoff;
- for clustering: entity to cluster, feature window, and intended use of clusters;
- for forecasting: target metric, time grain, horizon, expected seasonality, segment grain, available future driver scenarios, and whether scenario ranges are required;
- for CatBoost forecasting: prediction origin, target period, direct-vs-recursive horizon design, categorical columns, future plan snapshots, baseline models, and validation cutoffs;
- for basket/affinity: basket definition, item level, and minimum support/business threshold.

If the missing item blocks a defensible method, stop and ask. If analysis can continue only as weaker descriptive evidence, explicitly downgrade the method and conclusion status.

## Anti-Bullshit Mini Contract

Before every strong business conclusion, write or mentally verify this contract. In final notebook conclusions, include it explicitly when the conclusion is material.

```text
Утверждение:
Доказательство:
Проверка:
Ограничение:
Альтернативное объяснение:
Статус вывода:
```

Allowed `Статус вывода` values:

- `подтверждено`: direct data evidence supports the claim and sanity checks passed;
- `частично подтверждено`: direction is supported, but coverage, controls, sample size, or confounding limits strength;
- `не подтверждено`: available data do not support the claim;
- `недостаточно данных`: required data, period, metric, or comparison group is missing.

## Evidence Rules

Do not present correlation as causation unless the method has a credible comparison design and limitations are stated.

Every material claim must name:

- the source tables or files;
- the analysis grain;
- the period;
- the metric definition;
- the compared groups;
- the numeric result;
- the validation checks that protect the result.

For metrics or features calculated on large tables, also state when a calculation uses a task-specific non-vectorized method and why a vectorized NumPy/pandas implementation is not practical.

If evidence is descriptive, use Russian wording such as `данные показывают` or `паттерн согласуется с гипотезой`. Use causal wording such as `привело к` or `вызвало` only with a defensible design and explicit caveats.

If the evidence is weak, the correct output is a weaker conclusion, not a stronger narrative.

## ML And Statistical Guardrails

If an analysis uses a statistical test, confidence interval, causal design, or ML model, the notebook must document:

- why the method is appropriate for the question;
- the population, unit of analysis, time split, and target or treatment definition;
- baseline method or descriptive benchmark;
- validation design;
- leakage risks;
- uncertainty or error bars;
- business interpretation and limitations.

Do not optimize for a technical metric alone. State whether the result is useful for the business action the user can actually take.
