# Pre-Ship Gate

Use this skill before publishing changes or when the user asks whether a branch is ready.

This is a gate, not a deployment robot. Do not push, merge, release, or open a PR unless the user explicitly asked for that action or a GitHub publishing skill is also in scope.

## Gate Workflow

1. **Branch and diff**
   Identify current branch, base branch, changed files, commit list, and uncommitted changes. Abort if there is nothing to ship.

2. **Intent check**
   State what the branch appears to do. Compare delivered changes to the request, plan, PR body, TODOs, or commit messages. Flag scope creep and missing work.

3. **Required checks**
   Run the smallest relevant test, lint, type, build, browser, benchmark, or eval gates for the changed surface. Prefer repository-defined commands. Distinguish failures introduced by this branch from pre-existing failures.

4. **Risk review**
   For non-trivial diffs, apply `production-risk-review` logic or run that skill first. For contract-affecting changes, apply `contract-impact-analysis`. For backend performance claims, apply `backend-performance-evidence`.

5. **Docs drift**
   Update or flag docs only when the diff changes public behavior, config, deployment, architecture, developer workflow, benchmark expectations, or user-visible flows. Target specific docs; do not crawl all documentation.

6. **Release artifacts**
   Check whether version, changelog, migration notes, rollback notes, screenshots, benchmark results, or QA evidence are needed. Generate or update them only when they are part of the repo's existing release convention or the user asked.

7. **Publish readiness**
   Summarize whether the branch is ready, blocked, or ready with caveats. If publishing was requested, use the appropriate Git/GitHub workflow after the gate passes.

## Output

Use:

- Ship verdict
- Intent vs delivered
- Checks run and results
- Review, contract, performance, QA, or docs gates triggered
- Release artifacts changed or needed
- Residual risk and manual reviewer notes
