# Staged Plan Runner

Use this skill to execute an existing staged plan through its prompt pack and stage ledger. Do not use it to create the plan or prompts; use `architecture-design` for staged plans and `prompt-manager` for prompt packs.

## Core Contract

A runnable staged plan is described by exactly three durable artifacts:

- `plan_doc`: the architecture, implementation, migration, or rollout plan that explains what and why.
- `prompt_pack_dir`: the `.codex/agents/generated/<pack>/` directory that explains how to execute each stage.
- `stage_ledger`: the iteration journal that records current stage, status, blockers, evidence, and next-stage handoff.

Do not require or create `GOAL.md` by default. Codex Goal mode is only an optional execution mode over the same three artifacts.

If any of the three artifacts is missing, ambiguous, or not linked from the prompt pack or ledger, stop and report a blocker instead of inventing a fourth source of truth.

## Modes

- `manual_sequential`: run exactly the current requested stage or next allowed stage, update the ledger, then stop with the next prompt/stage to run.
- `goal_driven`: continue stage by stage while the ledger permits progress; stop only when the plan is `completed`, a stage is `blocked`, evidence is missing, user input is required, or safety/policy blocks execution.

Use `goal_driven` only when the user explicitly starts or asks for Goal mode, or when the active goal text clearly says to execute the whole prompt pack. Otherwise default to `manual_sequential`.

## Workflow

1. Read `.codex/AGENTS.md`.
2. Locate and read `stage_ledger`.
3. From the ledger or current prompt, confirm `plan_doc`, `prompt_pack_dir`, and execution mode.
4. Read only the current stage row, the relevant handoff notes, blockers, evidence, and the plan sections needed for the current stage.
5. Determine the current executable stage:
   - prefer ledger `current_stage`;
   - otherwise use the first `pending` stage whose previous required stage is `accepted`;
   - if status is ambiguous, stop as blocked.
6. Locate the stage prompt:
   - prefer the prompt path recorded in the ledger stage row;
   - otherwise match one prompt in `prompt_pack_dir` by stage id;
   - if zero or multiple prompts match, stop as blocked.
7. Read the selected stage prompt completely and follow its task-specific skill routing.
8. Execute only that stage scope. Preserve foreign changes from other chats and follow scoped staging policy.
9. Run required local gates and the nearest real-boundary validation surface. Tests alone are not acceptance unless the prompt explicitly justifies tests-only.
10. Update `stage_ledger` after validation and before the final response:
    - stage status: `accepted`, `blocked`, `skipped`, or `superseded`;
    - validation evidence and proof boundary;
    - file manifest;
    - foreign changes excluded and mixed-file status;
    - what the next stage must know;
    - whether the next stage is allowed.
11. In `manual_sequential`, stop after one stage and report the next allowed prompt.
12. In `goal_driven`, continue to the next allowed stage only if the ledger explicitly permits it.

## Stop Conditions

Stop and report `blocked` when:

- `plan_doc`, `prompt_pack_dir`, or `stage_ledger` is missing or inconsistent;
- the current stage cannot be determined from the ledger;
- the stage prompt cannot be identified uniquely;
- the previous required stage is not accepted and this is not a repair/unblock/supersede prompt;
- required validation evidence cannot be collected;
- the stage would require production proof before `main`, green CI, and deploy/sync;
- secrets, credentials, broad Git staging, Mac Studio path rules, or hook policy would be violated;
- user approval is required for branch/worktree/stash, production mutation, or destructive recovery.

Do not continue a dependent stage after a blocked stage.

## Reporting

Report in Russian unless a higher-priority instruction says otherwise.

For every completed stage, include:

- stage id and status;
- files changed by this stage only;
- evidence collected;
- ledger path updated;
- next allowed stage or blocker;
- residual risks.

For Goal mode, also state whether the overall staged plan is still running, blocked, or complete. Mark an active Codex goal complete only when the ledger shows the staged plan is complete and no required stage remains open.
