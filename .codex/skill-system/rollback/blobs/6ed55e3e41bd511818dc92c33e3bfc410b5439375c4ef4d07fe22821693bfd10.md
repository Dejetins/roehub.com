# Contract Impact Analysis

Use this skill when a change may alter the shape or semantics of a boundary that other code, users, or operators depend on.

## Identify Affected Contract Surfaces

Check whether the change affects any of these surfaces:

- public API behavior or payload shape,
- ports or boundary interfaces,
- DTO schemas,
- persisted storage schemas,
- configuration schemas, feature flags, or default resolution,
- service-call semantics: caller/callee ownership, auth model, timeout, retry, fallback, and error/status behavior,
- external side-effect semantics: idempotency keys, dedupe identity, reconciliation source of truth, and unknown-state handling,
- request-hash, cache-key, or persistence-identity semantics,
- logging, redaction, metric, trace, audit, ledger, and report semantics when consumers or operators rely on them,
- alerting and operational runbook triggers when runtime behavior or operator response changes,
- benchmark or rollout gates,
- browser-visible defaults or runtime behavior.

Treat semantics changes as contract changes even when field names stay the same.

Use source-of-truth files before relying on inference: API schemas/docs, DTO definitions, serializers/deserializers, port protocols, migrations, config loaders, feature flag resolution, cache/request identity builders, persisted snapshots, generated clients, and tests.

## Follow the Analysis Workflow

1. Identify the changed boundary and the likely consumers of that boundary.
2. Compare the old and new semantics, not just the old and new structure.
3. Search for likely consumers with `rg` across backend, frontend, tests, generated clients, docs, and adapters.
4. Classify each required impact dimension explicitly as `none`, `compatible-change`, `breaking-change`, or `unknown`.
5. If the change is breaking, record the migration, deprecation, rollout, rollback, test, and docs consequences.
6. If uncertainty remains, state the assumption and the unresolved risk instead of guessing.

## Use a Compatibility Checklist

When a contract surface may have a `compatible-change` or `breaking-change`, ask:

- Does any field become required, renamed, removed, or retyped?
- Does the error model or status behavior change?
- Does the auth model, timeout, retry, fallback, or degradation behavior of a service call change?
- Does idempotency, dedupe identity, or unknown-state handling change for external side effects or async processing?
- Does persistence shape, indexing, or identity behavior change?
- Do config defaults, flags, or profile-resolution rules change?
- Do logs, metrics, traces, audit events, ledgers, reports, or redaction rules change in a way operators or downstream tools depend on?
- Do alert triggers, severity, routing, or runbook actions change?
- Do cache keys, request hashes, or derived identities change?
- Does browser-visible behavior relied upon by users or operators change?

Treat additive optional fields, additional enum values, changed defaults, and relaxed validation as contract changes too. They may be compatible, but they still need consumer and rollout review.

## Report the Classification Explicitly

For non-trivial tasks, report each dimension as `none`, `compatible-change`, `breaking-change`, or `unknown`:

- public API contract
- port contract
- DTO schema
- persisted schema
- config schema
- request hash, cache key, or persistence identity semantics
- service-call auth/timeout/retry/error semantics
- external side-effect idempotency and unknown-state semantics
- logs, metrics, traces, audit, ledger, report, or redaction semantics
- alert or runbook semantics

If relevant, also report:

- benchmark or rollout gate impact
- performance risk on a verified hot path
- browser-visible behavior impact

Use a simple yes/no only for trivial work where the dimension is clearly unaffected.

## Guardrails

- Do not change a contract silently just because a local implementation becomes easier.
- Do not treat backward compatibility as preserved unless the semantics actually match.
- Do not hide migration or rollout needs for breaking changes.
- Do not classify internal refactors as public breaking changes unless an actual boundary or relied-upon behavior changes.
