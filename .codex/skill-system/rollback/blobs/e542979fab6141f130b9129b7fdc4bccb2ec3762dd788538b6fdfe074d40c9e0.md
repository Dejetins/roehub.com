# Browser QA Evidence

Use this skill when behavior is visible in a browser or a user flow must be verified end to end.

## Default Posture

Report-only by default. Fix bugs only when the user asked for test-and-fix or when the broader task already requires implementation.

Use the existing `playwright` skill for browser mechanics when needed.

Do not enter real secrets, modify production data, or execute destructive flows against a production-like target unless the user explicitly authorizes that action.

## QA Workflow

1. **Define target**
   Determine URL, auth state, changed pages/routes, browser viewport scope, data safety constraints, and whether the run is smoke, focused, or broad.

2. **Open the real target**
   Use a browser, not source inspection, as the source of truth for UI behavior. If no running app or URL is available, start the local server when appropriate or ask for the missing target.

3. **Orient**
   Capture initial page state. Check console errors, failed network requests, visible layout problems, and main navigation.

4. **Exercise user flows**
   Click links and buttons, submit forms, test empty/invalid/success states, verify loading and error states, and use realistic input. For SPA changes, test refresh, back/forward, and client-side navigation.

5. **Responsive and accessibility smoke**
   For user-facing layout changes, check at least one desktop and one mobile viewport, preferring product/repository viewport standards when defined. Note keyboard/focus or accessible-name problems when visible.

6. **Record evidence**
   For each issue, capture screenshot or trace evidence, reproduction steps, expected vs actual behavior, severity, and affected URL/state. Redact credentials and sensitive data.

7. **Verify fixes**
   If fixes are made, re-run the exact reproduction and capture after-evidence. Add regression coverage when the bug is behavior, not purely static visual polish.

## Severity Rubric

- `blocker`: prevents a primary user flow, exposes sensitive data, corrupts data, or blocks ship.
- `major`: breaks an important path or responsive state but has a workaround.
- `minor`: visible polish, copy, layout, or accessibility issue with limited workflow impact.
- `observation`: noteworthy behavior that is not clearly a defect.

## Output

Report:

- Target and scope tested
- User flows exercised
- Issues found with evidence
- Console/network summary, including whether errors were observed or not checked
- Fixes made, if any
- Verification and skipped checks, including screenshot or trace paths when captured
- Ship readiness: ready / ready with caveats / not ready
