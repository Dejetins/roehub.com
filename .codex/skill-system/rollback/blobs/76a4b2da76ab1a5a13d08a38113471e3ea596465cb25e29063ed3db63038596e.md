# Backend Quality Gates

Use this skill when backend changes need focused validation, when gates are failing, or when the task requires a disciplined check order instead of ad hoc command running.

## Start with the Smallest Relevant Gate Set

Use the repository's defined tooling and wrappers first. Before choosing commands, check the obvious sources of truth when present: `pyproject.toml`, `Makefile`, `tox.ini`, `noxfile.py`, task runners, and CI workflow files.

Begin with the narrowest checks that can validate the changed behavior:

1. Focused tests for touched behavior
2. Focused lint and type checks for touched paths
3. The original failing command when repairing a known gate failure
4. Broader suites only when the task, failing evidence, or repository policy requires them

Typical Python examples, when the repository uses these tools:

- `uv run pytest -q <target-or-empty>`
- `uv run ruff check <target-or-.>`
- `uv run pyright`
- `uv run mypy <target-or-package>`

If the repository exposes wrapper commands or a different check workflow, prefer those over generic commands. If a repository is not uv-based, adapt to its wrapper instead of forcing uv.

## Boundary with Adjacent Skills

- If a failure is a bug or regression and the root cause is unknown, use `root-cause-debugging` before editing production code.
- If the change affects externally relied-upon schemas, APIs, ports, config, cache keys, or persisted identity, layer `contract-impact-analysis`.
- If behavior is browser-visible, use `browser-qa-evidence` for runtime browser evidence; backend gates alone are not proof of UI correctness.

## Follow the Default Verification Order

1. Run the most focused deterministic test for the changed behavior.
2. Run focused lint and type gates for the touched files or package area.
3. Re-run the original failing gate when repairing a known failure.
4. Expand to broader test or type suites only after the focused gates are informative or when the prompt requires wider confidence.

## Triage Failing Gates Deliberately

Classify failures as one of:

- introduced by the current change,
- pre-existing but still on the required path,
- unrelated pre-existing repository failures,
- environmental or flaky behavior.

Do not blur introduced failures together with unrelated pre-existing ones.

If a gate failure is outside the requested scope, keep the change bounded and report it instead of broadening the task automatically.

## Handle Speed Mode Honestly

In a speed-focused task, still do at least one meaningful verification step:

- a minimal deterministic test,
- a focused smoke test,
- explicit manual verification steps with expected outcomes,
- `browser-qa-evidence` runtime verification for browser-visible behavior when relevant.

If checks are skipped, say so and explain why.

## Report Verification Clearly

Report:

- which checks were run,
- exact command and working directory when useful for reproduction,
- which checks were not run,
- why unrun checks were skipped,
- which failures are introduced versus pre-existing,
- which results are test evidence, runtime evidence, or inference.

## Guardrails

- Do not let unrelated edits expand the gate surface.
- Do not treat passing backend tests as proof of browser-visible correctness.
- Prefer deterministic checks over broad but noisy validation.
- Do not run broad auto-fix or formatter commands across unrelated files unless the task or repository policy requires it.
