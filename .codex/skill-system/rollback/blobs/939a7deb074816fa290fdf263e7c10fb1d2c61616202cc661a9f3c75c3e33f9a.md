# Publish CI Deploy

Use this skill as the single entrypoint for Roehub Git and GitHub delivery work.

The user should be able to say only: `use publish-ci-deploy for this change`.

After that, the skill must determine the current delivery stage and choose the correct route itself. It is not a narrow "open PR" helper. It owns the end-to-end delivery lifecycle around a local checkout.

## What This Skill Owns

- local repo and branch inspection
- repo, PR, and issue triage when that context is needed to continue delivery safely
- staging, commit, direct-main push, and draft PR creation only for explicitly requested branch/PR delivery
- unresolved PR review-comment inspection and follow-up
- GitHub Actions watch, log inspection, and actionable CI repair
- delivery-state handoff when the next state transition is outside the agent's control
- deployment to `Mac Studio` once the shipped revision is on `main`
- post-deploy smoke and runtime verification

This skill is Roehub-specific. Prefer repository runbooks, workflow files, and local scripts over generic GitHub habits.

## User-Facing Contract

When this skill is in scope, the agent SHOULD treat Git and GitHub delivery as an orchestration problem, not a series of unrelated requests.

The skill MUST:

- infer the current delivery stage from local and remote state
- choose the next required route itself
- continue automatically until the natural terminal state is reached
- avoid asking the user to restate the next obvious GitHub, CI, merge, deploy, or verification step

Natural terminal states:

- `green-pr`: the revision is published, PR review/CI is green, and the next step is a human merge or approval outside the agent's control
- `deployed`: the shipped revision is on `main`, deployment on `Mac Studio` is updated, and the required verification passes
- `blocked`: the flow cannot continue because of an explicit external blocker such as missing auth, ambiguous scope, missing repo access, required human approval, or an external failing system

## Prerequisites

- `gh --version`
- `gh auth status`
- local git checkout in the target repository
- explicit understanding of which local files or hunks belong to the delivery scope
- working SSH access to the configured Mac Studio host alias, usually `macstudio`
- repository runbooks available locally

If a prerequisite is missing, stop and report the concrete blocker.

Dirty `main` from parallel chats is not a missing prerequisite. Treat it as normal shared-checkout state when the owned delivery scope can be separated safely.

## Parallel Main Change Ownership

Roehub delivery may happen from a shared local `main` checkout where several Codex chats are editing different files at the same time.

The skill MUST:

- treat unrelated dirty files as foreign changes, not as a blocker by themselves;
- publish only files or hunks owned by the current request, prompt, stage ledger, file manifest, and verified diff;
- preserve foreign working-tree content exactly as it is; if foreign changes are already staged, unstage only those foreign paths narrowly before commit;
- never use broad staging, unstaging, reset, or commit commands that can include foreign work: `git add .`, `git add -A`, `git add --all`, `git add :/`, `git add -- .`, `git add *`, `git restore --staged .`, `git restore --staged :/`, `git restore --staged *`, `git reset HEAD .`, `git reset .`, `git commit -a`, `git commit --all`, `git commit -am`, or `git commit .`;
- use explicit path staging for owned files, and hunk staging for mixed files when safe;
- if a file contains mixed owned and foreign hunks that cannot be separated safely, block that file only and continue or report the remaining scoped delivery state;
- before every commit or push, run and inspect `git diff --cached --name-status`, confirm that every staged path belongs to the current delivery scope, and include `ROEHUB_SCOPED_STAGING_REVIEWED=1` in the commit/push command after inspection;
- if foreign paths are already staged, unstage only those paths with a narrow command such as `git restore --staged <path>`, never by resetting or reverting the working tree.

Final delivery reports MUST list:

- owned files or hunks included;
- foreign changes intentionally excluded;
- mixed files that required hunk staging or remained blocked.

## Mac Studio Path Contract

Use these paths exactly unless the repository runbook has been intentionally changed:

- SSH host alias: `macstudio`
- remote git checkout: `/Users/daniildegtyarev/Projects/roehub.com`
- production runtime tree: `/opt/roehub/app`

`/opt/roehub/app` is a synced runtime tree and may intentionally have no `.git`.
Do not run `git status`, `git pull`, `git fetch`, `git reset`, or branch commands inside `/opt/roehub/app`.

When remote git state matters, run git commands with:

```bash
git -C /Users/daniildegtyarev/Projects/roehub.com <command>
```

When production runtime files must be updated manually, sync from the remote git checkout or use the GitHub Actions deploy workflow's bundle semantics into `/opt/roehub/app`, then run bootstrap/reload/smoke from the runtime tree as appropriate. If the remote checkout is dirty, stale, detached, or not on the expected revision, do not treat `/opt/roehub/app` as a fallback checkout; report the checkout state and resolve it explicitly before syncing.

For SSH commands that include SQL, JSON, multiline shell bodies, or payloads with apostrophes/backticks/dollar signs, do not compose nested inline quotes. Pass the payload through quoted heredoc/stdin instead, for example `ssh macstudio 'zsh -lc "... clickhouse client --queries-file /dev/stdin"' <<'SQL' ... SQL`. Do not create temporary files solely to work around quoting.

## Mac Studio Proof Boundary

Keep these proof types separate:

- `target_host_readiness_pre_main`: pre-main, read-only host readiness evidence such as SSH reachability, configured paths, remote checkout state, environment presence, service manager status, current health, or current production smoke. This is useful for unblocking a stage, but it is not proof that changed code works in production.
- `read_only_existing_runtime_smoke`: pre-main observation of the currently deployed `/opt/roehub/app` runtime. It must not sync files, reload services, run migrations, mutate provider state, or claim changed-code validation.
- `post_main_production_runtime_proof`: changed-code production proof. It is valid only after the target revision is on `main`, relevant GitHub Actions/CI is green, deployment or verified sync from the `main` checkout to `/opt/roehub/app` has happened, and runtime smoke/browser/API/service verification passes.

If a prompt or stage asks for "Mac Studio target-runtime proof" before the revision has reached `main` with green CI, interpret that as a conflict. Collect only `target_host_readiness_pre_main` or `read_only_existing_runtime_smoke` if useful, then record the changed-code runtime proof as a deferred post-main handoff. Do not weaken the wording by calling pre-main evidence production proof.

## Stage Detection

Always resolve the current stage before acting.

1. Inspect local git context.
   - `git status -sb`
   - `git branch --show-current`
   - `git remote get-url origin`
   - diff or staged-file inspection as needed
2. Resolve GitHub context when relevant.
   - current branch PR if one exists
   - PR review state and unresolved actionable comments
   - GitHub Actions state for the branch PR or `main`
3. Resolve ship topology.
   - if the target revision is only local -> publish path
   - if the target revision is on a branch PR -> review and CI path
   - if the target revision is already on `main` -> deploy and verify path

Do not start from a fixed sub-workflow. Start from current state.

## Routing Rules

### 1. Triage Route

Use this route when the request is vague and the next delivery step depends on repository or PR state.

Handle directly:

- current branch PR lookup
- PR metadata summary
- issue or PR state needed to continue delivery
- changed-file and review-state orientation

This route is short-lived. Once the next concrete delivery action is clear, switch immediately to the narrower route below.

### 2. Publish Route

Use this route when the work exists locally and is not yet intentionally published.

Workflow:

1. confirm owned scope from `git status -sb`, the task/prompt/ledger/file manifest, and diff
2. if the working tree is mixed, classify owned, foreign, and mixed files; stage only owned files or owned hunks
3. inspect `git diff --cached --name-status`; if foreign paths are staged, unstage only those paths and re-check the staged diff
4. run mandatory local gates before publish:
   - `uv sync --locked --all-groups` when needed
   - `uv run ruff check .`
   - `uv run pyright`
   - `uv run pytest -q -ra`
   - `uv run python -m tools.docs.generate_docs_index --check`
5. choose publish strategy:
   - default to direct `main` delivery when publish is in scope and no branch/PR workflow was explicitly requested
   - do not create a branch unless the user explicitly requested branch-based or PR-based delivery
   - if the user explicitly requested branch/PR delivery and the checkout is on the default branch, create one `codex/{description}` branch for the delivery scope
   - if already on a real existing branch/PR path, continue that path only when it matches the user request or current delivery state
   - if the checkout is on an unexpected non-main branch and no branch/PR path was requested or already established, stop and report the branch conflict; do not push that branch or create another one
   - do not create worktrees, temporary checkouts, local folders, stashes, or auxiliary files as a workaround for mixed checkout state unless the user explicitly requested that exact artifact or workflow
6. commit tersely from the reviewed staged diff only
7. push `origin main` for direct-main delivery, or push with tracking only for an explicit branch/PR path
8. open a draft PR only for explicit branch/PR delivery or an already-established branch PR path
9. continue automatically into review and CI routes

If the user explicitly asked for direct `main` publishing, do not create a PR path that contradicts that instruction.

If the user asked to publish/ship and did not request branch/PR delivery, treat direct `main` delivery as the default after gates pass.

### 3. Review-Comments Route

Use this route when an existing PR has unresolved actionable review feedback.

Workflow:

1. resolve the PR from the current branch or explicit PR identifier
2. inspect unresolved review threads with `scripts/fetch_comments.py`
3. separate actionable changes from informational comments, approvals, duplicates, or already-resolved threads
4. implement the actionable fixes that are required to move delivery forward
5. run the smallest relevant verification locally
6. push the follow-up fix
7. continue automatically into CI watch

Do not reply on GitHub or resolve threads unless the user explicitly asked for that write action.

### 4. CI Watch and Repair Route

Use this route whenever the relevant GitHub Actions pipeline is pending or failing.

Workflow:

1. determine the correct pipeline:
   - branch PR checks for branch delivery
   - `push` pipeline on `main` for shipped revisions on `main`
2. wait for the pipeline
3. if checks fail, inspect them with `scripts/inspect_pr_checks.py`
4. fix only actionable failures attributable to the current diff or clear repository drift the user wants repaired
5. rerun the relevant local gates
6. push the follow-up fix
7. repeat until CI is green or a real external blocker remains

Do not treat local green as equivalent to GitHub green.

### 5. Merge or Handoff Route

Use this route when the branch PR is green but the revision is not yet on `main`.

Behavior:

- if the user asked for full shipping including merge and that action is safely available, perform it
- otherwise stop at the exact handoff boundary and summarize:
  - PR URL
  - review state
  - CI state
  - what remains for the revision to reach `main`

Do not ask the user whether the agent should wait for green PR if that is the obvious next stage. Wait automatically. Only stop when a real state transition lies outside the agent's authority or the user's request.

### 6. Deploy and Verify Route

Use this route only after the shipped revision is on `main`.

Workflow:

1. SSH into `macstudio`
2. verify the remote git checkout with `git -C /Users/daniildegtyarev/Projects/roehub.com status -sb` and `git -C /Users/daniildegtyarev/Projects/roehub.com rev-parse HEAD`
3. update or verify the intended `main` revision in `/Users/daniildegtyarev/Projects/roehub.com`, not in `/opt/roehub/app`
4. sync the deployable source bundle into `/opt/roehub/app` using the repository deploy workflow semantics (`rsync`/tar bundle), or rely on the green GitHub Actions deploy workflow when it already performed that sync
5. apply the repository runbook path from the synced runtime tree:
   - `bash scripts/macos/bootstrap_native_prod.sh`
   - restart only the impacted services when the impact is clear
   - otherwise run `bash scripts/macos/reload_launchd_services.sh prod`
6. if monitoring files changed, also run:
   - `brew services restart prometheus`
   - `brew services restart grafana`
7. always run:
   - `bash scripts/macos/smoke_prod.sh`
8. add targeted verification when needed:
   - auth or Keycloak surface changed -> auth curls and readiness checks
   - browser-visible behavior changed -> browser/runtime QA
9. if verification fails, inspect launchd status, brew services, `tailscale serve status`, and relevant logs, then fix and rerun verification

The verification collected in this route is `post_main_production_runtime_proof`. Do not use this route, or any manual equivalent that syncs/reloads `/opt/roehub/app`, for branch-only, dirty-checkout, or pre-main stage validation.

## Automatic Helper Skills

This skill is the only user-facing Git or GitHub delivery skill, but it MAY internally apply narrower procedures:

- `backend-quality-gates` for local gate selection and failing-gate triage
- `browser-qa-evidence` when browser-visible behavior changed
- `pre-ship-gate` only for explicit review-only or readiness-only tasks where no publish/deploy action is wanted

The user should not need to decide among those helpers.

## Guardrails

- Never silently stage unrelated local changes.
- Never treat unrelated dirty `main` state as a delivery blocker when the owned scope can be staged separately.
- Never use broad staging, unstaging, reset, or commit commands: `git add .`, `git add -A`, `git add --all`, `git add :/`, `git add -- .`, `git add *`, `git restore --staged .`, `git restore --staged :/`, `git restore --staged *`, `git reset HEAD .`, `git reset .`, `git commit -a`, `git commit --all`, `git commit -am`, or `git commit .`.
- Never commit or push without first inspecting `git diff --cached --name-status` for the exact staged path set and adding `ROEHUB_SCOPED_STAGING_REVIEWED=1` to the commit/push command after inspection.
- Never reset, clean, checkout, or revert foreign changes from other chats as a way to make the tree clean.
- Never create a branch, draft PR, worktree, temporary checkout, local folder, stash, or auxiliary workflow artifact unless the user explicitly requested that branch/PR/worktree/stash/folder workflow.
- Never skip `ruff`, `pyright`, or `pytest` without explicit user approval.
- Never stop early just to ask whether CI should be watched or fixed; that is baseline behavior of this skill.
- Never declare success while the relevant GitHub Actions pipeline is still failing.
- Never deploy to `Mac Studio` before the shipped revision is green in GitHub Actions.
- Never present `target_host_readiness_pre_main` or `read_only_existing_runtime_smoke` as proof that changed code works in production.
- Never satisfy a pre-main stage's Mac Studio requirement by syncing branch/dirty-checkout files into `/opt/roehub/app`; record `post_main_production_runtime_proof` as deferred until `main`, green CI, and deploy/sync.
- Never guess the SSH host alias, remote git checkout path, runtime tree, or service restart command.
- Never run git commands in `/opt/roehub/app`; use `/Users/daniildegtyarev/Projects/roehub.com` for git state and `/opt/roehub/app` only for synced runtime execution.
- Never inline nested shell quoting for SSH + SQL/JSON/multiline payloads; use quoted heredoc/stdin and keep payload parsing separate from local and remote shell parsing.
- Never restart unrelated production services when changed-path impact is clear.
- If service impact is ambiguous, state that and fall back to `bash scripts/macos/reload_launchd_services.sh prod`.
- If a failing check is external or non-actionable here, report it as a blocker instead of pretending the pipeline is complete.
- Do not reply on GitHub, resolve review threads, or merge a PR unless that write action is within the user's request.
