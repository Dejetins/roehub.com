# Backend Performance Evidence

Use this skill when performance is part of the task, when a backend change may affect a hot path, or when a claim about speed, throughput, latency, or allocation behavior needs support.

## Decide Whether the Path Is Truly Hot

Treat folder names, legacy comments, or the mere presence of Numba as non-evidence.

Treat a path as performance-critical only when at least one of these exists:

- production telemetry,
- realistic profiling,
- a perf smoke or benchmark suite,
- explicit project documentation or code-level markers.

If evidence is missing, treat the path as normal code and avoid premature optimization.

## Discover Existing Evidence First

Before creating a new benchmark or microbenchmark, search for existing:

- production telemetry or logs,
- profiling scripts or profiler output,
- perf smoke tests or benchmark suites,
- architecture docs that define benchmark policy,
- historical benchmark result files,
- code-level hot-path markers.

If the repository has a benchmark policy document for the affected area, follow it before inventing a new measurement shape. For example, if a backend task touches a path with `docs/architecture/**/benchmark_iterations/README.md`, read that file only for the affected area.

## Choose Evidence in Order

Prefer evidence in this order:

1. Production telemetry
2. Realistic profiling
3. Perf smoke or benchmark suite
4. Microbenchmark
5. Reasoned estimate

Label reasoned estimates explicitly.

## Follow the Performance Workflow

1. Bound the path and the metric before changing code.
2. Reuse existing perf smoke tests, benchmarks, or profiling setups when available.
3. Establish a baseline on the narrowest realistic workload that still reflects the real cost.
4. Optimize the dominant cost instead of polishing incidental code.
5. Re-measure with the same workload or the nearest equivalent evidence source.
6. Compare only equivalent workloads, stage boundaries, datasets, config, hardware class, and cache/warmup state.
7. If direct measurement is not feasible, say so and report the remaining risk.

## Measurement Hygiene

For measured claims, capture:

- command or harness used;
- commit, branch, config, fixture, dataset, and relevant hashes when available;
- hardware or runtime class when it materially affects results;
- cold vs warm path, JIT warmup, cache state, and thread/process settings;
- repeated runs or variance when timing noise can change the conclusion;
- CPU time, wall time, memory/allocation, IO, and network effects separately when they could dominate.

Do not compare a cold run to a warm run, a JIT compile path to an already-compiled path, or a service stage with extra production work to a narrower notebook/kernel stage without labeling the difference.

## Comparability Checklist

Before reporting a win, regression, or gate result, check:

- same workload semantics;
- same input size and representative distribution;
- same stage boundary;
- same config and feature flags;
- same baseline source and acceptance threshold;
- same hardware class or an explicit reason the comparison is still useful;
- same measurement mode for cold/warm cache, JIT, and threading.

If these are not true, report the result as directional evidence, not acceptance evidence.

## Handle Verified Hot Paths Carefully

Inside a verified hot path:

- prefer low-allocation and data-oriented logic in tight loops,
- avoid deep polymorphic dispatch when it adds measurable overhead,
- avoid tiny abstractions that add cost without protecting a real boundary,
- keep invariants explicit while preserving or improving the measured path.

If the path is assumed to be hot but measurements do not support that assumption, challenge it and fall back to normal maintainability-first code.

If Numba typing, `@njit`, `prange`, `fastmath`, cache behavior, JIT warmup, ufunc/gufunc, or thread configuration is central to the result, also use `numba`.

## Report Results Explicitly

Report:

- whether the path is a verified hot path,
- which evidence source was used,
- the baseline used for comparison,
- the dominant cost that was targeted,
- whether the result is measured or inferred,
- whether the comparison is acceptance evidence or only directional evidence,
- residual regression risk.

Use this compact report shape when performance is a main deliverable:

- `Scope`: path, metric, and workload.
- `Baseline`: source, command, result, and why it is comparable.
- `Change`: dominant cost targeted and implementation summary.
- `Result`: new measurement, delta, variance if relevant, and pass/fail against threshold.
- `Limits`: missing measurements, non-comparable factors, or residual regression risk.

## Guardrails

- Do not claim a performance win without comparable before-and-after evidence.
- Do not let a microbenchmark outweigh realistic workload evidence.
- Do not hide missing measurements; state the limitation directly.
- Do not tune incidental code before identifying the dominant cost.
- Do not weaken correctness, contracts, determinism, or numerical policy for speed unless the tradeoff is explicit and accepted.
