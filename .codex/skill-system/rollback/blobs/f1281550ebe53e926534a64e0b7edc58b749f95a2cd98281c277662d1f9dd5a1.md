# Prompt Manager

Use this skill when the deliverable is a prompt, prompt pack, prompt template, agent instruction, or prompt-routing update. It creates executor-ready prompt files; it does not replace implementation, review, QA, performance, browser, GitHub, or deployment skills.

## Source Order

Read only what is needed, in this order:

1. Platform/system/developer instructions already in force.
2. Repository `AGENTS.md` files, especially precedence, invariants, skill routing, verification, and output rules.
3. The user's request and explicit constraints.
4. Existing prompt templates, prompt agents, or prompt examples relevant to the task.
5. Existing old/current documentation and the target new-documentation pattern for the changed area.
6. Previous executor reports, state snapshots, or acceptance criteria when continuing an iteration.
7. Local code/docs only when they are needed to name real entrypoints, contracts, tests, or routes.

For Roehub, use `.codex/agents/promt_manager.toml` as reference input when present, and use `.codex/promt_template.md` as the current executor-prompt shape. Do not treat either file as higher priority than `.codex/AGENTS.md`.

For Roehub prompts that involve Mac Studio deploy, production runtime verification, remote benchmark execution, or SSH host operations, include the Mac Studio path contract from `.codex/AGENTS.md`: SSH alias `macstudio`, remote git checkout `/Users/daniildegtyarev/Projects/roehub.com`, runtime tree `/opt/roehub/app`, and the rule that git commands run only against the checkout while `/opt/roehub/app` is updated by deploy workflow or explicit rsync/tar bundle semantics. Also carry the Mac Studio proof/deploy boundary contract: pre-main checks may be `target_host_readiness_pre_main` or `read_only_existing_runtime_smoke`, while changed-code production proof is `post_main_production_runtime_proof` and requires `main`, green CI, deployment/sync, and runtime verification. Carry the remote command quoting contract: SSH commands with SQL, JSON, or multiline payloads must use quoted heredoc/stdin, not nested inline quotes or temporary files created only to dodge quoting.

## Prompt Engineering Rules

- Put the task, constraints, context, and output format in clearly separated sections.
- Be specific about scope, non-goals, acceptance criteria, and failure/blocker behavior.
- Provide grounded context and exact references instead of asking the executor to rediscover everything.
- Split complex work into ordered steps, but avoid over-prescribing obvious local mechanics.
- Use few-shot examples only when format imitation is important; keep example formatting consistent.
- Remove contradictions, stale instructions, legacy fields, and broad-reading habits.
- Prefer bounded context acquisition with reading budgets, stop conditions, and conditional bundles.
- Require the smallest meaningful verification surface for the task.
- For non-trivial implementation stages, do not let verification collapse to lint/type/unit tests only; require the nearest meaningful end-to-end or real-boundary evidence.
- For browser-visible work, require runtime browser evidence when available and relevant.
- For Roehub browser-visible or authenticated-browser prompt artifacts, carry the browser auth contract from `.codex/AGENTS.md`: default username `smoke_e2e_keycloak`, password source of truth on `macstudio` at `/Users/daniildegtyarev/.config/roehub/roehub.env` key `ROEHUB_SMOKE_E2E_PASSWORD`, no raw password in prompts, logs, screenshots, traces, reports, or ledgers, and blocked-auth reporting when no secret source is available.
- For performance work, require baseline, measurement method, and evidence before claims.
- For contract-affecting work, require explicit compatibility and rollout handling.
- For change work, require documentation continuity: old/current docs are read and updated, a new doc artifact is created, and both use the same documented shape.
- For prompt packs that implement a plan, require a stage execution ledger that records every stage status, handoff context, blockers, evidence, and next-stage notes.
- For prompt packs that implement a plan, require an explicit staged execution contract linking `plan_doc`, `prompt_pack_dir`, and `stage_ledger`. Do not create or require `GOAL.md` unless the user explicitly asks for that artifact.
- For prompt packs that implement architecture plans, carry forward the plan's conditional integration and operational requirements instead of flattening them into generic test-only tasks.
- For Roehub prompt packs, default to `main` execution. Do not instruct executors to create a branch unless the user explicitly requested one branch for the whole prompt pack; never create one branch per stage. Do not create branch-specific worktrees, temporary checkouts, local folders, stashes, or auxiliary files unless the user explicitly requested that exact artifact or workflow.
- For Roehub implementation, publishable, or staged prompts, include a `change_ownership` contract: parallel dirty `main` is expected, each chat owns only its task files/hunks, foreign changes from other chats must be preserved and excluded, and a dirty worktree is not a blocker by itself.
- Generated prompts must forbid broad staging/unstaging/commit commands such as `git add .`, `git add -A`, `git add --all`, `git add :/`, `git add -- .`, `git add *`, `git restore --staged .`, `git restore --staged :/`, `git restore --staged *`, `git reset HEAD .`, `git reset .`, `git commit -a`, `git commit --all`, `git commit -am`, and `git commit .`; require explicit path or hunk staging plus `git diff --cached --name-status` before commit or push and `ROEHUB_SCOPED_STAGING_REVIEWED=1` in commit/push commands after inspection.
- For Roehub prompt packs that mention Mac Studio, target runtime, production runtime, `/opt/roehub/app`, deploy, or smoke evidence, require explicit proof-boundary labels. Pre-main Mac Studio evidence must be labeled `target_host_readiness_pre_main` or `read_only_existing_runtime_smoke`; changed-code production runtime proof must be labeled `post_main_production_runtime_proof` and deferred until the revision is on `main`, CI is green, and deployment/sync has occurred.
- For every prompt-manager task that creates, rewrites, audits, migrates, reviews, extends, fixes, or finalizes prompt packs, prompt files, prompt templates, executor prompts, agent instructions, or skill-routing instructions, require one cold-head review before reporting the artifact as ready.

## Documentation Continuity Contract

For implementation, migration, refactor, cleanup, bug-fix, or behavior-change prompts, documentation is part of the deliverable, not an optional nearby cleanup.

Generated prompts must require the executor to:

- identify the old/current documentation that describes the affected behavior, contract, operation, plan, or user-visible surface;
- include those old/current docs in `always_read`, `task_entrypoints`, or a clearly named conditional bundle when they are needed to bound the task;
- update old/current docs in the same change so they no longer describe stale behavior as current;
- create a new Markdown documentation artifact for the delivered change unless a higher-priority user instruction or repository policy explicitly forbids new docs;
- choose one canonical documentation shape before writing: existing template, sibling document, generated evidence folder pattern, ADR/runbook pattern, or project docs convention;
- make old/current doc updates and the new doc artifact use that same shape: matching front matter style when present, heading order, section names, table schema, naming convention, language choice, and evidence/report blocks;
- include the new doc path in expected touches or possible secondary touches and include the old doc path in the reading manifest;
- require docs verification, including the repository docs-index check when Markdown docs change.

If no old/current documentation exists within the bounded reading budget, the generated prompt must say so explicitly, require the executor to create the new doc in the selected canonical shape, and report the absence instead of inventing an old-doc path.

If the prompt template has no dedicated documentation-continuity section, encode this contract consistently in front matter, `## Requirements (Must)`, `# Reading manifest`, `# Acceptance criteria`, and the existing `## Documentation` implementation-constraints block. Do not invent a new docs shape per prompt.

## Stage Execution Ledger Contract

For any prompt pack, staged rollout, multi-stage implementation plan, migration plan, or implementation plan expected to be executed through agent prompts, the generated artifacts must create or reuse one stage execution ledger.

Purpose:

- keep a durable handoff between stages;
- prevent later stages from rediscovering prior decisions, blockers, validation results, or contract impact;
- make skipped, blocked, superseded, and accepted states explicit;
- give the next executor compact context without loading full chat history or old prompt files.

Default Roehub template:

```text
.codex/agents/stage_execution_ledger_template.md
```

Default ledger placement:

```text
docs/architecture/<area>/<plan-slug>-stage-reports/<plan-slug>-stage-ledger.md
```

If a local plan already has an equivalent `iteration-ledger` or stage-report ledger, reuse and update that file instead of creating a duplicate.

Generated prompt packs must:

- create the ledger before or with the first implementation prompt;
- link the prompt pack to exactly three execution artifacts: `plan_doc`, `prompt_pack_dir`, and `stage_ledger`;
- set execution mode to `manual_sequential` by default, and use `goal_driven` only when the user explicitly asks Codex to continue through the whole prompt pack as a goal or autocontinuation flow;
- state that Codex Goal mode is an optional runner mode over the same three artifacts, not a requirement to create `GOAL.md`;
- include the ledger path in `context_sources.always_read` or the narrowest relevant `task_entrypoints`;
- include the ledger path in `expected_primary_touches` or `possible_secondary_touches` for every stage that must update it;
- for Roehub staged implementation prompt packs, default to including the ledger in `expected_primary_touches` for every stage prompt because every stage must record accepted, blocked, superseded, evidence, or handoff state;
- require the executor to update the ledger after validation and before the final report;
- require blocked stages to record `blocked` status, reason, severity, evidence, owner or next action, and whether the next stage is allowed;
- require accepted stages to record concise results, changed files or contracts, verification evidence, publish/deploy handoff when applicable, and "what the next stage must know";
- forbid starting a later dependent stage when the previous required stage is not accepted, unless the prompt is explicitly a repair, unblock, or supersede task;
- keep secrets, tokens, raw credentials, cookies, ciphertext, passphrases, and sensitive exchange/provider responses out of the ledger.

Prompt artifacts themselves still follow the prompt language contract. For Roehub, generated executor prompts stay in English unless explicitly requested otherwise. The stage ledger follows repository documentation language rules; architecture-stage ledgers are Russian by default.

## Staged Prompt-Pack Execution Contract

Prompt packs are runnable when these three artifacts are present and linked:

- `plan_doc`: the plan that explains what and why;
- `prompt_pack_dir`: the `.codex/agents/generated/<pack>/` directory with executable stage prompts;
- `stage_ledger`: the journal that records current stage, status, blockers, evidence, and next-stage handoff.

Generated prompt packs must not create a fourth goal source of truth by default. `GOAL.md` is allowed only when the user explicitly requests that file.

Execution modes:

- `manual_sequential`: the executor runs one requested or next allowed stage, updates the ledger, reports the next prompt, and stops.
- `goal_driven`: the executor may continue stage by stage while the ledger explicitly permits progress, and stops on `blocked`, `completed`, missing evidence, missing linked artifact, or required user approval.

Generated stage prompts must:

- include front matter `prompt_pack_execution` with `mode`, `plan_doc`, `prompt_pack_dir`, `stage_ledger`, `goal_mode_optional=true`, and `goal_artifact_required=false`;
- route execution/continuation tasks to `staged-plan-runner` when the executor is asked to run the plan rather than create or revise prompts;
- instruct the executor to derive the current stage from `stage_ledger`, not from chat memory or prompt filename guesses;
- stop as blocked if any of the three artifacts is missing, ambiguous, or inconsistent.

## Prompt-Pack Branch Policy Contract

Roehub prompt packs execute on `main` by default. A separate branch is allowed only when the user explicitly asks for branch-based execution or branch-based delivery for that prompt pack.

Generated prompt packs must:

- define one shared `branch_policy` for the pack when branch work is mentioned;
- set `default_branch: main`;
- state `separate_branch_allowed: false` unless the user explicitly requested a branch;
- when a branch is explicitly requested, set one `single_allowed_branch` for the whole prompt pack and require every stage to reuse it;
- forbid branch-specific worktrees, temporary checkouts, local folders, stashes, or auxiliary files unless the user explicitly requested that exact artifact or workflow;
- forbid per-stage branch creation and stage-specific names such as `*-stage-00`, `*-stage-01`, or `*/stage-01`;
- forbid speculative `git switch -c`, `git checkout -b`, `git branch`, and `git worktree add` commands when the user did not request them;
- require final delivery back to `main` or an explicit blocked/deferred delivery record, according to the repository publish/deploy workflow.

If the source plan or prior chat already contains multiple stage-specific branches, generated prompts must treat that as cleanup context, not as a pattern to repeat. The next prompt should converge to the single pack branch or `main`, depending on the user's explicit branch instruction.

## Parallel Main Change Ownership Contract

Roehub agents may work concurrently in the same local `main` checkout. Generated prompts must assume unrelated dirty changes can exist and must not treat that as a reason to stop, create a branch, create a worktree, or stash.

Generated prompts must:

- define `change_ownership` in front matter for implementation, publishable, and staged prompts;
- state that owned changes are only the files/hunks required by the current prompt;
- instruct executors to preserve and exclude all foreign changes, including unrelated staged changes;
- require hunk-level staging for mixed files, or a file-specific blocker if safe separation is impossible;
- forbid broad staging/unstaging/commit commands: `git add .`, `git add -A`, `git add --all`, `git add :/`, `git add -- .`, `git add *`, `git restore --staged .`, `git restore --staged :/`, `git restore --staged *`, `git reset HEAD .`, `git reset .`, `git commit -a`, `git commit --all`, `git commit -am`, and `git commit .`;
- require `git diff --cached --name-status` review before commit or push, then require `ROEHUB_SCOPED_STAGING_REVIEWED=1` in the commit/push command;
- require final reports to list owned files included, foreign changes excluded, and mixed-file limitations.

## Validation Depth Contract

Generated prompts for implementation, prompt-pack stages, rollout stages, migrations, runtime changes, or architecture-plan execution must define validation depth explicitly. Local tests are a gate, not the default definition of done.

Generated prompts must require the executor to choose and record the nearest meaningful acceptance surface for the changed behavior:

- pure domain logic: focused unit/property/invariant tests may be sufficient when no boundary changes;
- API or use-case boundary: route/use-case smoke through real request/DTO mapping plus focused tests;
- persistence or migrations: migration/schema check and repository/database integration evidence;
- browser-visible behavior: real browser/runtime QA plus static/tests as supporting evidence;
- Roehub authenticated browser flows: use the smoke Keycloak account username and host-local password source from `.codex/AGENTS.md`, forbid password leakage in artifacts, and require blocked-auth reporting if the password source is unavailable;
- runtime/ops changes: deployed or target-host smoke, health checks, metrics, service manager evidence, and runtime file/config parity when relevant;
- Mac Studio pre-main checks: use `target_host_readiness_pre_main` for SSH/path/env/service-readiness evidence and `read_only_existing_runtime_smoke` for observing the currently deployed runtime; neither is changed-code production proof;
- Mac Studio changed-code production checks: use `post_main_production_runtime_proof` only after the target revision is on `main`, relevant GitHub Actions/CI is green, deployment/sync from the verified `main` checkout to `/opt/roehub/app` has occurred, and runtime smoke/browser/API/service verification is collected;
- performance-sensitive paths: baseline plus comparable benchmark/profile evidence;
- external integrations: safe real-adapter/runtime smoke where available, with secrets and destructive actions excluded;
- ship-ready stages: CI/deploy status plus post-deploy or target-environment smoke.
- Mac Studio deploy or benchmark stages: remote git state is checked under `/Users/daniildegtyarev/Projects/roehub.com`; production runtime verification for changed code may execute under `/opt/roehub/app` only as `post_main_production_runtime_proof`; prompts must not tell executors to run git commands in `/opt/roehub/app` or to deploy branch/dirty checkout code as a substitute for post-main proof.
- Mac Studio SSH + SQL/JSON/multiline stages: prompts must require quoted heredoc/stdin payload passing (`<<'SQL'`, `<<'JSON'`, `--queries-file /dev/stdin`, `query=@-`, or equivalent) and must forbid fragile nested inline `--query "..."` forms when the payload contains its own quotes. Do not introduce temporary files solely for quoting.

Tests-only acceptance is valid only for trivial, internal-only changes that have no public contract, persistence, browser-visible, runtime, ops, performance, or delivery impact. When a generated prompt uses tests-only acceptance, it must require the executor to state why this exception is safe.

For prompt packs and staged plans, encode validation depth in:

- front matter: `validation_strategy` with depth, acceptance surfaces, and any tests-only exception;
- front matter for Mac Studio/runtime stages: explicit `proof_boundary` with one of `target_host_readiness_pre_main`, `read_only_existing_runtime_smoke`, or `post_main_production_runtime_proof`;
- `## Requirements (Must)`: local gates plus real-boundary or end-to-end evidence where relevant;
- `# Work plan`: run local gates first, then the selected acceptance-surface validation;
- `# Acceptance criteria`: stage is not accepted until the selected real-boundary evidence is recorded or a tests-only exception is justified;
- `# Quality gates`: include commands or explicit manual/runtime checks for the selected surface;
- stage execution ledger: record validation depth, evidence path, residual risk, and whether the next stage is allowed.

## Architecture Plan Carry-Forward Contract

When generating prompt packs, staged implementation prompts, or executor prompts from an architecture plan, preserve the plan's conditional architecture coverage. Do not require every stage to include every operational section; require the relevant sections only where the source plan or changed surface makes them applicable.

Generated prompts must carry forward these details when present or required by the affected surface:

- service calls and integration handoffs: caller, callee, contract, auth model, timeout/retry behavior, and failure behavior;
- planned files and artifacts by stage: code, config, infra, migration, docs, runbooks, prompt artifacts, and evidence targets;
- affected documentation: old/current docs to update, new docs or runbooks to create, and docs-index verification when applicable;
- errors, retry, and idempotency: concrete error/status classes where known, retryable vs non-retryable rules, idempotency or dedupe identity, and unknown-state handling;
- logging and redaction: what can be logged, what must be summarized/hashed/redacted, and what is forbidden in logs, metrics, traces, ledgers, reports, and provider payloads;
- alerts and operational monitoring: alert rules, trigger signals, severity/owner when known, and runbook actions.

For exchange execution, money-moving, provider submit, durable async processing, or any external side effect, generated prompts must forbid blind retry after an unknown result. Require reconciliation, provider-state lookup, durable ledger check, or another explicit source-of-truth check before retrying the side effect.

If the source architecture plan omits one of these details for a surface where it appears required, the generated prompt must either:

- mark it as an implementation blocker or pre-stage clarification, or
- scope the stage so it does not touch that risk surface.

## File Manifest Contract

For staged prompt packs, generated prompts must preserve a strict file/artifact contract.

Each stage prompt must define expected touches using these groups when applicable:

- code;
- config / infra / migrations;
- docs / runbooks;
- prompt artifacts;
- stage ledger and evidence artifacts.

Every stage final report must include a file manifest:

- `created`;
- `modified`;
- `deleted`;
- `outside_expected_paths`;
- justification for every file outside the prompt's expected paths.

If the source plan does not provide enough per-stage file coverage, stop and mark this as a prompt-pack blocker instead of producing broad prompts.

## Cold-Head Review Gate

For every prompt-manager task that creates, rewrites, audits, migrates, reviews, extends, fixes, or finalizes prompt packs, prompt files, prompt templates, executor prompts, agent instructions, or skill-routing instructions, do not report the artifact as ready on author self-audit alone.

Before final output:

- run exactly one independent read-only cold-head subagent automatically when subagents are available;
- otherwise perform the same checklist locally and label it `cold self-review fallback`;
- use `architecture-review/references/cold-head-plan-prompt-pack-review.md` as the review instructions;
- fix every Blocker and every High finding that affects contract, runtime topology, side-effect retry, secrets/redaction, deploy path, or stage advancement;
- maintain a finding adoption checklist: fixed, intentionally not applied with reason, or residual non-blocking risk;
- after fixes, run a local follow-up check against the same checklist instead of launching another subagent by default;
- include the review verdict and remaining non-blocking risks in the final report.
- include this exact structured receipt block before using readiness language such as `ready`, `final`, `готово`, `завершено`, or `подготовлено`:

```text
Cold-head review: completed
Mode: independent subagent | cold self-review fallback
Review scope: ...
Review instructions: architecture-review/references/cold-head-plan-prompt-pack-review.md
Verdict: Release | Release after fixes | Block
Blockers fixed: ...
Local follow-up check: completed | not needed | blocked
Residual risks: ...
```

The cold-head review must check the architecture plan, generated prompts, stage ledger, per-stage file manifest, affected docs/runbooks, service-call table, exact entrypoints for claims about existing components, browser auth/redaction defaults when browser flows are in scope, isolated executability of every stage, and traceability from architecture requirements to prompt instructions, ledger updates, file touches, and validation evidence.

Do not report a prompt-manager artifact as ready, final, complete, finished, `готов`, `завершен`, or `подготовлен` unless the structured cold-head receipt block is present in the final response. If the review was skipped, unavailable, or unresolved, state the artifact is not ready and report the blocker instead of using readiness language.

## Workflow

1. **Classify the prompt.** Decide whether it is for implementation, review, planning, debugging, QA, performance, delivery, or another prompt-writing task.
2. **Resolve authority.** Identify which `AGENTS.md`, templates, user constraints, and prior results control the output. State conflicts only when material.
3. **Resolve documentation continuity.** For change work, name old/current docs to update, the new doc artifact to create, the canonical docs shape to reuse, and the docs verification gate.
4. **Resolve validation depth.** Decide whether tests-only is sufficient; otherwise name the real-boundary, runtime, browser, benchmark, adapter, CI/deploy, or end-to-end evidence required for acceptance.
5. **Resolve architecture carry-forward.** For architecture-plan execution, identify relevant service calls, planned artifacts by stage, affected docs/runbooks, retry/idempotency, redaction, alerts, and any missing blockers.
6. **Resolve stage execution ledger.** For prompt-pack or staged plan work, name the ledger path, whether it is new or existing, the template/shape to reuse, and the required per-stage update rule.
7. **Resolve prompt-pack execution mode.** For prompt packs or staged plans, link `plan_doc`, `prompt_pack_dir`, and `stage_ledger`; default to `manual_sequential`; use `goal_driven` only when the user asks for Goal mode/autocontinuation; do not create `GOAL.md` unless explicitly requested.
8. **Resolve branch policy.** For prompt packs, default to `main`; if and only if the user explicitly requested a branch, name one branch for the whole pack and forbid stage-specific branches. Do not create branch-specific folders, worktrees, stashes, or auxiliary files unless the user explicitly requested them.
9. **Resolve change ownership.** For implementation, publishable, and staged prompts, define owned files/hunks, foreign-change exclusion, mixed-file handling, forbidden broad staging commands, and the `git diff --cached --name-status` pre-commit check.
10. **Resolve file manifest.** For staged prompt packs, ensure each stage has expected code/config/infra/docs/runbook/prompt/evidence touch zones and a required final-report manifest for created/modified/deleted/outside-expected files.
11. **Resolve traceability.** Map material architecture requirements to prompts, stage-ledger updates, file/artifact touches, and validation evidence. Missing links are blockers for plan-derived prompt packs.
12. **Build a compact context ledger.** Carry forward only current facts: completed work, open items, contract changes, touched paths, risks, documentation state, validation evidence state, stage ledger state, prompt-pack execution state, branch policy state, change ownership state, and next focus.
13. **Route skills.** Select the narrowest applicable skills by exact frontmatter `name`; do not ask the executor to preload skills that are merely adjacent.
14. **Bound context acquisition.** Name entrypoints, old/current docs, stage ledger, conditional bundles, consult-if-needed references, reading budget, and stop conditions.
15. **Write prompt files.** Create one complete `.md` file per prompt artifact in the target generated prompt folder.
16. **Cold-head review gate.** For every prompt-manager artifact creation, rewrite, audit, migration, review, extension, fix, or finalization task, run exactly one automatic independent cold-head subagent review when subagents are available; otherwise run the local fallback. Fix blocking findings before final report and verify the fixes locally.
17. **Self-audit before output.** Check for ambiguity, contradictions, missing documentation continuity, missing stage ledger, missing prompt-pack execution links, weak validation depth, missing branch policy, missing change ownership, missing file manifest, missing verification, missing traceability, missing applicable architecture carry-forward, excessive context, wrong skill names, invalid paths, and template drift.

## Prompt Artifact Storage

Every generated prompt must be saved as a standalone Markdown file.

Default storage root:

```text
.codex/agents/generated
```

Rules:

- Never leave a requested prompt only in chat when repository file access is available.
- Create one dedicated folder per prompt pack under `.codex/agents/generated/<pack_folder>/`.
- If the user provides a pack folder name, use it as the folder name after removing unsafe path traversal.
- If no folder name is provided, infer a short lowercase slug from the task, using `-` or `_` consistently with nearby generated folders.
- For a single prompt without an explicit pack, still create a folder under `.codex/agents/generated/<prompt_slug>/`.
- Each prompt file must be complete and executable on its own; do not make one prompt depend on another file for required instructions.
- Use stable, sortable filenames for packs, such as `01-implement-<topic>.md`, `02-review-<topic>.md`, or `<prompt_name>.md` when ordering is not relevant.
- Do not create README, index, manifest, or auxiliary documentation files unless the user explicitly asks for them, except for the mandatory stage execution ledger required by prompt packs and staged plan implementation.
- Do not write generated prompts outside `.codex/agents/generated` unless the user explicitly provides a different repository-controlled target and the active `AGENTS.md` permits it.

For example, a new prompt pack named `new_promt_pack_folder` must write its prompt files under:

```text
.codex/agents/generated/new_promt_pack_folder/
```

If updating an existing prompt pack, modify only the prompt files needed for the requested change and preserve unrelated prompt files.

## Skill Routing In Generated Prompts

Generated prompts must tell the executor which skill to use, when to use it, and why. Keep this routing compact and conditional.

Rules:

- Use exact skill names from the current environment or the repository skill-routing contract.
- Prefer one primary workflow skill; layer additional skills only at real boundary crossings.
- State timing: before implementation, during investigation, during verification, before ship, or only if a blocker appears.
- Do not instruct the executor to read every skill body at startup.
- If a required skill is unavailable, instruct the executor to state the limitation and use the nearest task-bounded equivalent.
- Do not route to `prompt-manager` unless the executor's task is itself prompt creation, rewrite, migration, audit, review, extension, fix, finalization, or skill-routing prompt design.

Common routing:

- Architecture review, refactor analysis, migration review, or docs-sync -> `architecture-review`.
- New architecture, bounded-context design, service integration, ADR, or phased migration design -> `architecture-design`.
- Bugs, regressions, failing tests, stack traces, or "worked before" reports -> `root-cause-debugging`.
- Branch, PR, or diff review focused on production risk -> `production-risk-review`.
- API, DTO, persistence, config, cache identity, or browser-visible default compatibility -> `contract-impact-analysis`.
- Backend test, lint, type-check, or failing-gate triage -> `backend-quality-gates`.
- Backend performance claims, profiling, benchmark design, hot-path work -> `backend-performance-evidence`.
- Numba/JIT kernel work, `@njit`, `prange`, `fastmath`, ufunc/gufunc, typing, or threading diagnostics -> `numba`.
- Browser-visible QA, screenshots, console/network checks, forms, navigation, responsive checks, or QA report -> `browser-qa-evidence` plus an available browser surface such as Browser plugin or `playwright`.
- Ship readiness, PR handoff, release evidence, docs drift before publishing, or "is this ready?" checks -> `pre-ship-gate`.
- End-to-end Roehub Git/GitHub/CI/deploy/post-deploy verification -> `publish-ci-deploy`.
- Prompt creation, prompt rewrite, prompt migration, prompt audit, or skill-routing prompt design -> `prompt-manager`.
- Executing, continuing, or auditing execution state for an existing staged plan or prompt pack from `plan_doc` + `prompt_pack_dir` + `stage_ledger` -> `staged-plan-runner`.

For Numba tasks, route both layers when needed: use `numba` for JIT-specific implementation choices and `backend-performance-evidence` for measurement, baseline, and performance claims.

## Recommended Executor Prompt Shape

When a repository supplies a prompt template, follow it unless it conflicts with higher-priority instructions. For Roehub executor prompts, preserve the `.codex/promt_template.md` shape and keep these sections:

- front matter with scope, language, context sources, hard requirements, task toggles, skill routing, quality gates, expected touches, and safety notes;
- front matter with branch policy, proof boundary, runtime env sources, remote command quoting, stage execution ledger, and file manifest when those surfaces are applicable;
- front matter with `prompt_pack_execution` for prompt packs or staged plans, linking `plan_doc`, `prompt_pack_dir`, `stage_ledger`, and execution mode;
- front matter with change ownership for implementation, publishable, and staged prompts that may run in the shared `main` checkout;
- `# Task`;
- `## Context / Current State`;
- `## Requirements (Must)`;
- `## Requirements (Should)`;
- `## Requirements (Nice-to-have)`;
- `# Context acquisition protocol`;
- `# Reading manifest`;
- `# Work plan (agent should follow)`;
- `# Acceptance criteria (Definition of Done)`;
- `# Implementation constraints`;
- `# Files to indicate (expected touched areas)`;
- `# Non-goals`;
- `# Quality gates (must run and pass)`;
- `# Final output: report format (strict)`.

For prompts that involve changes, encode documentation continuity in the same places every time:

- front matter: old/current docs, new doc artifact, canonical docs shape, and docs gate;
- `## Requirements (Must)`: update old/current docs and create the new doc artifact;
- `# Reading manifest`: old/current docs and the shape/template source;
- `# Acceptance criteria`: old docs updated, new docs created, matching shape verified;
- `## Documentation`: same-shape docs rule and docs-index requirement.

For implementation prompts, encode validation depth in the same places every time:

- front matter: `validation_strategy` with depth, acceptance surfaces, tests-only exception if any, and required evidence;
- front matter for Mac Studio/runtime prompts: `proof_boundary` distinguishing host readiness, read-only existing-runtime smoke, and post-main production runtime proof;
- `## Requirements (Must)`: require local gates plus real-boundary/end-to-end validation unless tests-only is explicitly justified;
- `# Work plan`: run tests first, then validate through the selected runtime, browser, API, persistence, benchmark, adapter, CI/deploy, or target-host surface;
- `# Acceptance criteria`: stage acceptance depends on recorded validation evidence, not only successful test commands;
- `# Quality gates`: include the commands or manual/runtime checks needed for the selected acceptance surface.

For prompt packs or staged plan implementation, encode the stage execution ledger in the same places every time:

- front matter: `stage_execution_ledger` with path, plan doc, current stage, update requirement, and template/source shape;
- `context_sources.always_read` or `task_entrypoints`: the ledger path with a reason tied to handoff state;
- `## Requirements (Must)`: update the ledger after validation and before final report;
- `# Work plan`: verify previous required stage status before implementation, then update ledger after checks;
- `# Acceptance criteria`: ledger updated with status, evidence, blockers, next-stage notes, and publish/deploy handoff when applicable;
- `## Documentation`: ledger is a required plan-execution doc, not optional auxiliary documentation.

For prompt packs or staged plan implementation, encode prompt-pack execution in the same places every time:

- front matter: `prompt_pack_execution` with `mode`, `plan_doc`, `prompt_pack_dir`, `stage_ledger`, `goal_mode_optional=true`, and `goal_artifact_required=false`;
- `## Requirements (Must)`: the executor must use the linked plan, prompt pack, and ledger as the source of truth and must not require `GOAL.md`;
- `# Work plan`: determine current stage from `stage_ledger`; in `manual_sequential`, run one stage and stop; in `goal_driven`, continue only while the ledger explicitly permits the next stage;
- `# Acceptance criteria`: no stage is accepted or advanced unless the ledger is updated with status, evidence, blocker state, and next-stage allowance.

For prompt packs, encode branch policy in the same places every time:

- front matter: `branch_policy` with `default_branch`, `separate_branch_allowed`, optional `single_allowed_branch`, and `stage_specific_branches_forbidden=true`;
- `## Requirements (Must)`: no branch creation unless explicitly requested by the user for the whole pack; no branch-specific worktrees, temporary checkouts, folders, stashes, or auxiliary files unless explicitly requested;
- `# Work plan`: start from `main` by default, or reuse the one allowed branch when explicitly requested;
- `# Acceptance criteria`: no per-stage branches were created, no unrequested worktrees/folders/files were created, and any branch usage is recorded in the stage ledger and final report.

For staged prompt packs, encode the file manifest in the same places every time:

- front matter: expected code/config/infra/docs/runbook/prompt/evidence touch groups;
- `## Requirements (Must)`: final report must list created, modified, deleted, and outside-expected files;
- `# Acceptance criteria`: no unreported file changes and every outside-expected file has justification;
- stage execution ledger: record the file manifest summary and any outside-expected path rationale.

For prompt packs generated from architecture plans, encode conditional architecture carry-forward in the same places every time:

- front matter: affected service calls, planned artifacts by stage, affected docs/runbooks, retry/idempotency, redaction, alerts, or `N/A` with a short reason;
- `## Requirements (Must)`: preserve the relevant architecture-plan constraints and treat missing required details as blockers;
- `# Reading manifest`: include the architecture plan, old/current docs, affected runbooks, and stage ledger needed for the stage;
- `# Work plan`: verify the previous stage status, then implement only the planned code/config/infra/docs areas for that stage;
- `# Acceptance criteria`: service/error/redaction/alert/docs obligations are met where applicable and recorded in the stage ledger.

For prompt packs generated from architecture plans, also encode traceability:

- front matter or a compact section: material plan requirement -> stage prompt(s) -> ledger update -> expected touches -> validation evidence;
- `# Work plan`: verify that each material requirement has at least one implementation or explicit `N/A`/blocker path;
- `# Final output`: report any requirement that could not be linked to an artifact or validation surface.

Avoid legacy broad-reading prompt shapes, including flat `primary_docs`, flat `expected_touched_paths`, duplicate mandatory reading lists, or `# Required reading (do first)`.

## Context Discipline

Use a layered reading map:

- `always_read`: repository contract, compact state, latest verified result.
- `task_entrypoints`: two to four primary files, symbols, routes, or old/current docs that anchor the work.
- `conditional_bundles`: grouped files read only if a stated condition applies.
- `consult_if_needed`: broader docs or adjacent areas for blockers, ambiguity, conflicts, or failing gates.

Default pre-implementation budget for ordinary implementation prompts:

- no more than eight files;
- roughly 35k-50k tokens;
- expand only for blockers, failing gates, contract ambiguity, benchmark threshold conflicts, or explicit review/audit scope.

Stop reading once changed contracts are identified, touched files are bounded, old/current docs, new docs, and canonical docs shape are identified for change work, acceptance criteria are implementable, and no unresolved public API or persistence-contract ambiguity remains.

## Quality Gates And Evidence

Prompts should distinguish:

- unit/integration test evidence;
- end-to-end or real-boundary evidence;
- browser runtime evidence;
- deployed or target-environment runtime evidence;
- benchmark/profile evidence;
- code-based inference;
- unverified assumptions.

Use repository-defined commands when available. For Roehub backend prompts, prefer targeted forms of:

- `uv run ruff check <target-or-.>`;
- `uv run pyright`;
- `uv run pytest -q <target-or-empty>`;
- `uv run python -m tools.docs.generate_docs_index --check` when Markdown docs change.

## Output Contract

If the user asks for a prompt artifact, save it to `.codex/agents/generated/<folder>/...md` and report the file path. Do not paste the full prompt in chat unless the user explicitly asks for inline output. If the user asks to edit prompt files, make the scoped edits and report changed files plus validation.

Before returning, verify:

- the prompt directly answers the user's request;
- every prompt artifact is saved as a standalone `.md` file under `.codex/agents/generated`;
- prompt pack folders are dedicated and path-safe;
- prompt packs and staged-plan prompts link `plan_doc`, `prompt_pack_dir`, and `stage_ledger`, define `manual_sequential` or `goal_driven`, and do not require `GOAL.md` unless explicitly requested;
- prompt packs define the branch policy, do not create per-stage branches, and do not create unrequested branch-specific worktrees, folders, stashes, or auxiliary files;
- all skill names are exact;
- skill routing includes timing and purpose;
- `AGENTS.md` precedence and safety invariants are preserved;
- context loading is bounded and conditional;
- acceptance criteria are measurable;
- change-work prompts identify old/current docs to update, new docs to create, and the canonical docs shape to reuse;
- prompt packs and staged-plan prompts identify the stage execution ledger to create or update;
- staged prompt packs include the ledger as an expected primary touch for every stage that records outcome;
- staged prompt packs include per-stage file manifest requirements and outside-expected-path justification;
- architecture-plan prompt packs preserve applicable service-call, planned-artifact, affected-docs, retry/idempotency, redaction, alert, and runbook requirements;
- prompt-manager artifacts completed the cold-head review gate, or clearly state the local fallback and residual risk;
- the final response includes the exact structured cold-head receipt block when any prompt-manager artifact is reported as ready, complete, final, updated, or prepared;
- cold-head findings have an adoption checklist and every Blocker/High is fixed or explicitly reported as unresolved;
- material architecture requirements trace to prompt instructions, ledger updates, file touches, and validation evidence;
- non-trivial implementation prompts require real-boundary/end-to-end validation, or explicitly justify why tests-only acceptance is safe;
- quality gates match the task surface;
- browser, performance, contract, and ship gates are included only when relevant;
- no obsolete template keys or stale historical details remain.
