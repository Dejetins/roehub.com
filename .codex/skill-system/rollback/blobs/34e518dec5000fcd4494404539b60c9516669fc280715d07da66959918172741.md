# Numba for CPU JIT Performance

Numba is most useful when a numerical kernel is hot, data is already in NumPy arrays or scalars, and Python overhead is the bottleneck. This skill is intentionally CPU-only, pinned to Numba 0.60.0 behavior, and aimed at 64-bit systems, including Apple Silicon.

## Use This Skill When

- A NumPy-heavy loop or kernel is on the critical path.
- Vectorized NumPy alone is not expressive enough for the algorithm.
- You need CPU parallelism with `parallel=True` and `prange`.
- You need a CPU ufunc or gufunc with `@vectorize` or `@guvectorize`.
- You are debugging Numba typing errors, unsupported-feature errors, or poor parallel speedup.
- You need evidence-based benchmarking before or after a Numba change.

## Do Not Reach for Numba First When

- The bottleneck is I/O, networking, pandas orchestration, or Python object churn.
- Most time is already spent inside optimized BLAS, LAPACK, or NumPy primitives.
- The function is tiny or called too infrequently for JIT cost to amortize.
- An algorithmic change would dominate any likely JIT speedup.

## Platform Notes

- Numba 0.60.0 officially supports macOS 10.9 and later, with unofficial support on M1/Arm64.
- Automatic parallelization is only available on 64-bit platforms.
- On macOS, OpenMP-backed threading may require `intel-openmp` or `llvm-openmp`; on Apple Silicon, verify the selected threading layer instead of assuming parallel kernels are configured correctly.

## Default Workflow

1. Measure first. Isolate the real hotspot before adding decorators.
2. Move only the hot numerical kernel into its own function.
3. Feed the kernel NumPy arrays, NumPy scalars, or other homogeneous values.
4. Start with `@njit(cache=True)`.
5. Warm up once before measuring steady-state runtime.
6. Verify compilation quality with `inspect_types()` and `signatures`.
7. Add `parallel=True` and `prange` only when iterations are independent or a supported reduction is present.
8. Add `fastmath=True` only when the caller accepts relaxed floating-point semantics.
9. Tune threads and threading layers only after parallel speedup is proven.
10. Keep orchestration, validation, I/O, and object-heavy code outside the compiled region.

## Baseline Pattern

Use this as the default starting point for a hot CPU kernel:

```python
from time import perf_counter
import numpy as np
from numba import njit


@njit(cache=True)
def l2_norm_sq(x):
    acc = 0.0
    for i in range(x.shape[0]):
        acc += x[i] * x[i]
    return acc


x = np.random.random(1_000_000)
l2_norm_sq(x)  # warm up: compile once before timing

t0 = perf_counter()
for _ in range(20):
    l2_norm_sq(x)
elapsed = perf_counter() - t0
```

## Parallel Reduction Pattern

Use `prange` only when iterations are independent or when Numba can infer a supported reduction:

```python
import numpy as np
from numba import njit, prange


@njit(parallel=True, cache=True)
def sum_sqrt(x):
    acc = 0.0
    for i in prange(x.shape[0]):
        acc += np.sqrt(x[i])
    return acc
```

After the first compiled call, inspect what happened:

```python
sum_sqrt(x)  # compile
sum_sqrt.parallel_diagnostics(level=4)
```

If diagnostics show serialization or unsupported transforms, treat `parallel=True` as unproven and benchmark again after changes.

## CPU Ufunc and GUFunc Patterns

Use `@vectorize` when the scalar kernel is simple and you want NumPy ufunc behavior such as broadcasting or reduction methods:

```python
from numba import vectorize


@vectorize(["float64(float64, float64)"], target="cpu")
def fast_add(x, y):
    return x + y
```

Use `@guvectorize` when the kernel naturally works on small array blocks:

```python
from numba import guvectorize


@guvectorize(["void(float64[:], float64[:])"], "(n)->(n)", nopython=True, target="cpu")
def clip01(inp, out):
    for i in range(inp.shape[0]):
        x = inp[i]
        if x < 0.0:
            out[i] = 0.0
        elif x > 1.0:
            out[i] = 1.0
        else:
            out[i] = x
```

Prefer plain `@njit` when a compiled loop is enough. Use `@vectorize` or `@guvectorize` when NumPy ufunc or gufunc semantics are the real requirement.

## Typed Containers

Prefer NumPy arrays first. If the algorithm truly needs dynamic containers inside compiled code, use `numba.typed` containers instead of regular Python containers.

```python
from numba import njit, types
from numba.typed import List


@njit
def build_offsets(n):
    out = List.empty_list(types.int64)
    acc = 0
    for i in range(n):
        acc += i
        out.append(acc)
    return out
```

Typed containers are much slower from the Python interpreter than from compiled code. Keep container-heavy operations inside the jitted function boundary.

## Core Rules

- Prefer `@njit` as the default CPU entry point.
- Keep the compiled region small and focused on the hotspot.
- Feed compiled functions homogeneous, predictable types.
- Pass globals and configuration as arguments instead of reading mutable globals.
- Keep pandas, arbitrary Python objects, and business logic out of the compiled region.
- Move the loop into compiled code rather than calling a tiny jitted scalar function from a Python loop.
- Avoid repeated allocation in hot inner loops when preallocation or output buffers are possible.
- Warm up before timing. First-call latency is compilation, not steady-state execution.
- Use signatures only when startup latency, dispatch control, or API constraints justify them.
- Use `cache=True` when cold-start compile cost matters, but remember that cache invalidation has limits.

## What `cache=True` Actually Buys You

- It writes compiled results to a file-based cache so subsequent process starts can skip some compilation work.
- It does not mean every specialization is always available up front.
- Cached globals are treated as constants at compile time.
- Changes in functions imported from other files may not invalidate the cache correctly.

Do not describe ordinary first-call compilation as "cached" unless `cache=True` is actually enabled.

## Performance Knobs

### `parallel=True`

- Use only for independent iterations or supported reductions.
- Benchmark it. Some kernels get slower from scheduler overhead or poor memory locality.
- Do not mutate lists, sets, or dictionaries inside a `prange` region.

### `fastmath=True`

- Use only when relaxed floating-point semantics are acceptable.
- Re-check tolerances and numerical invariants after enabling it.

### `nogil=True`

- Useful when compiled code runs concurrently with other Python or Numba threads.
- Treat it as a concurrency feature, not a default speed knob.

### Threading controls

- `NUMBA_NUM_THREADS` sets the maximum thread count and must be set before Numba import.
- `numba.set_num_threads(n)` changes the active count at runtime, up to that maximum.
- `numba.threading_layer()` tells you which backend was selected after a parallel function has run.
- `NUMBA_THREADING_LAYER` or `numba.config.THREADING_LAYER` lets you force a backend before parallel compilation occurs.
- On a machine with outer parallelism, reduce Numba threads to avoid oversubscription.

### Parallel diagnostics

Use one of these when validating a parallel kernel:

```bash
NUMBA_PARALLEL_DIAGNOSTICS=1 python script.py
```

```python
compiled.parallel_diagnostics(level=4)
```

## Supported-Features Reality Check

Numba supports a subset of Python and NumPy in `nopython` mode, not the whole language.

- Strings, exceptions, lists, sets, dictionaries, and `random` support are partial and feature-specific.
- Many NumPy operations work well, but support is not universal. Check the supported NumPy reference when in doubt.
- `np.linalg` support may depend on optional runtime pieces such as SciPy-backed bindings. Benchmark before replacing existing linear algebra with hand-written loops.
- Behavior can differ from Python semantics around globals, integer width, bounds checking, and exception behavior.

When a kernel starts to accumulate dynamic Python behavior, either simplify the kernel or move that behavior out of the compiled region.

## Common Failure Modes

### TypingError or unsupported-feature errors

Usually means one of:

- a Python feature is unsupported in `nopython` mode,
- argument types are inconsistent across calls,
- object-heavy code leaked into the kernel.

First response:

1. reduce the kernel to the failing operation,
2. check supported Python or NumPy features,
3. normalize input types before the jitted boundary.

### Type unification problems

Branches returning incompatible types will fail compilation. Make return types consistent across all paths.

### Untyped list problems

An empty list with no inferable element type is a common failure. Either append a known type inside the kernel or use `numba.typed.List`.

### Object mode or `@jit(forceobj=True)` is slow

Object mode usually provides little to no speedup. Treat it as a debugging or fallback state, not a success criterion.

### Globals and closures

Compiled functions capture global values at compile time. Pass changing values as explicit arguments.

### Random seeding

Seed inside compiled code if you want to affect Numba's RNG state:

```python
import random
from numba import njit


@njit
def seed_rng(seed):
    random.seed(seed)
```

### Parallel container mutation

Mutating containers inside `prange` is not thread-safe. Use array outputs, reductions, or per-iteration independent writes.

## Debugging and Inspection

- `compiled.inspect_types()` shows inferred types and helps detect object-heavy code.
- `compiled.signatures` shows compiled signatures already seen.
- `NUMBA_DISABLE_JIT=1` disables JIT so you can compare behavior against pure Python quickly.
- If you need low-level debug info for compiled CPU code, `@njit(debug=True)` exists, but use it intentionally because it changes optimization and code size tradeoffs.

## Minimal Acceptance Checklist

- The hotspot was measured before and after the change.
- First-call compilation cost was excluded from steady-state timing.
- The compiled function runs in `nopython` mode.
- Any `parallel=True` change was verified with diagnostics and benchmark data.
- Any `fastmath=True` change was validated against numerical expectations.
- Thread count and oversubscription were considered for the actual runtime environment.
