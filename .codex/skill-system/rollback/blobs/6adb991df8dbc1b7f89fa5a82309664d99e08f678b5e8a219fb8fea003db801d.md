# Root Cause Debugging

Use this skill when the task is to debug or fix a concrete failure.

## Core Rule

Do not patch symptoms first. Establish a specific, testable root-cause hypothesis before editing production code.

Preserve the evidence needed to review the fix: exact command, URL or flow, input data shape, logs or stack trace, relevant environment assumptions, and current diff/status when they matter.

## Boundary with Adjacent Skills

- Use `backend-quality-gates` when the main work is selecting, running, or triaging backend gates.
- Use `browser-qa-evidence` when the symptom requires real browser reproduction or verification.
- Use `contract-impact-analysis` before finalizing a fix that changes a boundary, persisted shape, config/default behavior, cache key, request hash, or externally visible semantics.

## Workflow

1. **Collect the symptom**
   Capture the exact error, failing command, affected user flow, logs, stack trace, reproduction steps, and expected behavior. Ask one concise question only if the failure cannot be reproduced or located from available context.

2. **Trace the path**
   Read the code from entry point to failure. Use `rg` for references. Check recent history for affected files with `git log --oneline -20 -- <paths>` and, when useful, `git blame` when a regression is plausible.

3. **Reproduce or localize**
   Prefer a focused failing test, command, browser flow, or minimal script. If reproduction is impossible, gather enough evidence to localize the fault and state the uncertainty.

4. **Form a hypothesis**
   Write one sentence: `Root-cause hypothesis: <cause> because <evidence>.`
   Do not implement until the hypothesis is supported by code, logs, tests, or observed behavior.

5. **Test the hypothesis**
   Add temporary instrumentation only when needed, then remove it. If several hypotheses fail, pause before editing production code: summarize what evidence ruled them out, then form a narrower investigation plan or report the blocker.

6. **Fix narrowly**
   Change the smallest set of files that addresses the confirmed cause. Do not refactor adjacent code unless the root cause is structural and the user asked for that scope.

7. **Add regression coverage**
   Add or update a test that fails without the fix and passes with it when feasible. If the pre-fix red run was not captured, say so. If no test framework exists or the bug is not realistically testable, explain the gap and provide the strongest alternate verification.

8. **Verify**
   Re-run the original reproduction plus the focused test. Expand checks only when the change crosses shared boundaries.

## Report Shape

End with:

- Symptom
- Root cause
- Fix
- Regression coverage
- Verification run
- Residual risk or skipped checks
