# Architecture Review

Use this skill for no-code or review-first tasks where understanding, scope control, and evidence quality matter more than immediate implementation.

## Mandatory Cold-Head Gate

For any architecture review, architecture-document review, development-plan review, implementation-plan review, migration-plan review, refactor-plan review, rollout-plan review, docs/code drift review, or architecture artifact completion/correction/hardening, load `references/cold-head-plan-prompt-pack-review.md` and apply it as the mandatory review gate.

When subagents are available, start exactly one independent read-only cold-head subagent automatically and pass those instructions plus the bounded artifacts under review. If subagents are unavailable, perform the same checklist locally and label the result as `cold self-review fallback`. After the cold-head pass, the main agent owns the fix loop: incorporate required artifact edits, run a local follow-up check against the same checklist, and do not start a second cold-head subagent unless the user explicitly asks for another independent pass.

Before any final response that reports an architecture or prompt-manager artifact review as ready, final, complete, finished, `готов`, `завершен`, or `подготовлен`, include this exact structured receipt block:

```text
Cold-head review: completed
Mode: independent subagent | cold self-review fallback
Review scope: ...
Review instructions: architecture-review/references/cold-head-plan-prompt-pack-review.md
Verdict: Release | Release after fixes | Block
Blockers fixed: ...
Local follow-up check: completed | not needed | blocked
Residual risks: ...
```

Do not use readiness language for reviewed architecture documents, plans, prompt packs, executor prompts, or skill-routing artifacts unless that structured receipt is present. If the cold-head pass is unavailable or unresolved, state that the artifact is not ready and report the blocker.

## Build Context Selectively

Read only enough material to answer the review question safely.

Prefer this order when available:

1. The user-provided plan, architecture doc, review question, or changed artifact
2. Repository `AGENTS.md`
3. README and task entrypoints
4. `docs/architecture/README.md` or the nearest architecture index
5. Only the architecture documents relevant to the changed bounded context or concern
6. `.codex/PLANS.md` only for multi-iteration, roadmap, or checkpointed work

Do not turn a local review into a repo-wide documentation crawl unless the task explicitly asks for it.

## Run the Review Workflow

1. State the review scope and the bounded context or subsystem under review.
2. Separate observed facts from inferred risks as you read.
3. When code and docs are available, compare the current code and the directly relevant docs rather than trusting either alone.
4. Identify contract, architectural, operational, and verification risks.
5. Identify what already exists that should be reused instead of rebuilt.
6. Record the evidence quality behind each material finding.
7. State what is intentionally not in scope when deferring adjacent work.
8. Recommend only the smallest set of changes needed to resolve the material risks.

## Assess Development Plans

Use this workflow when the user asks to evaluate, review, harden, or risk-check a development plan, implementation plan, migration plan, refactor plan, rollout plan, or multi-step engineering roadmap.

Keep the task in review mode. Do not redesign the target architecture unless the plan is missing a decision that prevents safe execution. If target-state design becomes the main task, switch or hand off to `architecture-design`.

For each material plan assessment, check:

- goal and target state clarity;
- scope, non-scope, and bounded context;
- observed current state and assumptions;
- fixed decisions and constraints;
- architectural fit and dependency direction;
- reuse of existing code, docs, contracts, and tests;
- step decomposition and increment size;
- step sequencing and prerequisites;
- parallelization opportunities and coordination points;
- contract, API, event, DTO, config, cache, and persistence impact;
- data migration, backfill, consistency, and source-of-truth handling;
- integration semantics: timeout, retry, idempotency, failure behavior;
- service-call map when services, contexts, workers, queues, SDKs, or external providers participate: who calls whom, contract, auth model, timeout/retry policy, and error behavior;
- concrete error/status classes, retryable vs non-retryable handling, idempotency or dedupe identity, and unknown-state behavior for external side effects or money-moving/provider submit flows;
- security, privacy, secrets, compliance, and trust boundaries;
- logging and redaction boundaries for logs, metrics, traces, ledgers, reports, provider payloads, account/order identifiers, secrets, and PII;
- operational behavior: config, feature flags, rollout, degradation;
- observability: logs, metrics, traces, audit events, alerts;
- alert rules, trigger signals, severity, owner, and runbook actions for runtime, worker, queue, scheduler, exchange-execution, or user-impacting failures;
- planned files and artifacts by stage for staged plans: code, config, infra, migrations, docs, runbooks, prompt artifacts, and evidence paths;
- verification strategy for each material risk;
- rollout, cutover, rollback, and recovery path;
- documentation updates or explicit doc gaps;
- risk register, open questions, and required decisions;
- execution readiness for engineers.

Score each area as:

- `OK`: sufficiently covered and executable;
- `Partial`: directionally covered but needs clarification;
- `Gap`: the plan omits a required element or decision;
- `Risk`: present but unsafe, inconsistent, or likely to cause rework;
- `N/A`: not applicable to this plan;
- `Unknown`: the plan makes or depends on a claim that cannot be verified from the provided evidence.

Assign severity only to material issues:

- `Blocker`: unsafe to start or likely to cause critical failure, data loss, broken contracts, or unrecoverable rollout;
- `High`: likely to cause major rework, outage risk, compatibility break, or security/compliance issue;
- `Medium`: manageable risk requiring clarification before or during implementation;
- `Low`: quality, maintainability, or documentation improvement.

For every `Gap`, `Risk`, or `Unknown`, provide:

- observed fact;
- inference;
- source;
- affected contract or boundary;
- verification needed;
- smallest recommended change to make the plan executable.

When a structured plan-review answer is useful, adapt `references/output-templates.md`.

## Evidence Ledger

For each material finding, keep enough evidence for a reviewer to audit the claim:

- `observed fact`: what code, docs, config, or tests currently show;
- `inference`: the risk or implication, labeled as an inference;
- `source`: the narrow path, symbol, doc section, or command output that supports it;
- `affected contract`: public API, port, DTO, persistence, config, cache identity, runtime workflow, or none;
- `verification`: what would prove the fix or disprove the risk.

Do not treat historical intent, folder names, or stale plans as stronger evidence than current code, tests, docs, and runtime behavior.

## Check Completeness Without Expanding Scope

For non-trivial reviewed designs, development plans, migrations, refactors, or architecture docs, include:

- the primary data flow or state transition,
- realistic failure modes for new or changed code paths,
- verification needed for each material risk,
- docs that must change if architecture, contracts, config, or workflows change,
- parallelization opportunities only when work can be split cleanly by module.

For service-integration, exchange-execution, runtime, or staged-delivery plans, also check whether the plan conditionally covers:

- caller/callee and contract/auth/timeout/retry/error behavior for service calls;
- planned code/config/infra/docs/runbook/evidence artifacts by stage;
- affected strategy, identity, exchange-connection, secret-management, operations, and execution runbooks when those areas are in scope;
- explicit rule for unknown external side-effect state before retry;
- redaction rules for sensitive logs, metrics, traces, ledgers, and reports;
- alert triggers and runbook actions for operational monitoring.

For prompt-pack or staged-agent execution, also check:

- each stage can be executed by a fresh agent from the prompt and named context alone, without relying on hidden chat history;
- material architecture requirements trace to generated prompts, stage-ledger updates, expected file/artifact touches, and validation evidence;
- the stage ledger is included in required context and expected touches for every stage that records accepted, blocked, superseded, or handoff state;
- every stage has a strict file/artifact manifest: created, modified, deleted, expected docs/runbooks, and evidence targets;
- prompts explain how to report and justify any touched file outside expected paths;
- each prompt verifies the previous required stage status before implementation;
- generated prompts preserve architecture decisions instead of re-opening worker/app/service topology unless the plan marks that choice as a blocker.

Do not turn this into a release checklist. If the question is primarily PR readiness, use `production-risk-review` or `pre-ship-gate` instead.

If contract compatibility becomes the main question, layer `contract-impact-analysis`.
If the review turns into new target-state design, switch or hand off to `architecture-design`.

## Structure Findings Rigorously

Present review output using these buckets:

- observed state,
- key findings,
- contract or architecture risks,
- recommended changes,
- verification or validation needed,
- open uncertainties.

For development-plan assessments, also include:

- verdict: `Ready`, `Ready with changes`, or `Not ready`;
- assessment matrix with status and severity;
- missing plan elements;
- minimal plan edits needed before execution;
- verification needed before implementation starts.

For cold-head plan/prompt-pack reviews, include:

- verdict: `Release`, `Release after fixes`, or `Block`;
- artifacts reviewed: plan, prompts, ledger, docs/runbooks, and entrypoints;
- blocking findings and required fixes;
- main-agent adoption status for Blocker and High findings after edits;
- residual non-blocking risks;
- whether the review was independent subagent review or local fallback.
- the exact structured cold-head receipt block when the artifact is reported as ready, final, complete, `готов`, `завершен`, or `подготовлен`.

When useful, add `what already exists` and `not in scope` sections so the review can prevent both reinvention and silent deferral.

Do not present a proposal as if it were already implemented.

## Sync Documentation Narrowly

When the reviewed plan or architecture change affects contracts, architecture boundaries, operational behavior, or browser-visible workflows:

- recommend updates to the directly affected docs;
- or record the doc gap explicitly when docs are intentionally deferred.

Distinguish:

- outdated docs,
- missing docs,
- optional but useful docs.

Avoid broad cleanup of unrelated documentation.

Do not modify implementation artifacts as part of this skill. If the user explicitly asks to update documentation, keep the edit narrow and limited to the reviewed contract, boundary, workflow, or operational behavior.

## Guardrails

- Keep reading concern-grouped and stop when the review is evidence-sufficient.
- Prefer targeted doc recommendations over repository-wide doc normalization.
- Keep the response clearly in review mode.
- Do not implement code changes under this skill.
- Cold-head reviewers must not edit files; they only report readiness findings and smallest required fixes.
