# Production Risk Review

Use this skill for review-first work. Do not make code changes unless the user explicitly asks for fixes after the review.

## Scope

Review the current branch, PR, or provided diff against the stated intent. If no intent is provided, infer it from the user request, commit messages, PR body, TODOs, or changed files and label the inference.

## Review Order

1. **Establish intent and base**
   Identify base branch, changed files, and the intended outcome. Note whether the diff is small, broad, or contract-affecting.

2. **Scope drift**
   Check for unrelated refactors, files outside the requested area, missing requirements, and partial implementations. Separate `scope creep` from `missing requirement`.

3. **Production-risk pass**
   Prioritize:
   - public API, DTO, persisted schema, config, or default behavior changes,
   - SQL/data safety, migrations, rollback and backfill risk,
   - idempotency, request hashes, cache keys, dedupe keys, and retry semantics,
   - concurrency, races, async/sync boundary changes,
   - auth, authorization, tenant isolation, secret handling,
   - LLM/user-content trust boundaries and unsafe rendering or execution,
   - background jobs, queues, side effects, and external integrations.

4. **Test and verification pass**
   Identify which changed behaviors need unit, integration, E2E, regression, benchmark, or eval coverage. Call out gaps that can hide production regressions.

5. **Docs and operations pass**
   If behavior, contracts, config, deployment, or workflows changed, check whether docs, runbooks, changelog, or release notes need updating. Do not scan every doc by default; target only likely affected docs.

6. **Optional independent view**
   If the user explicitly asked for an independent, adversarial, or second-model review, use the available mechanism for that environment. Do not spawn subagents or run external model tools solely because this skill triggered.

## Finding Standards

Lead with findings. Each finding should include severity, confidence, file/line when available, why it matters, and the smallest fix or decision needed.

Suppress style preferences unless they create real maintenance, correctness, or operational risk.

## Output

Use:

- Findings, ordered by severity
- Scope drift or missing requirements
- Test and verification gaps
- Docs or release notes needed
- Open questions or assumptions

If there are no material issues, say that clearly and mention remaining verification risk.
