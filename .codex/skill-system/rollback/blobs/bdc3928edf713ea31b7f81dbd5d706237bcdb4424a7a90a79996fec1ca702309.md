# Architecture Design

Use this skill for design-first work: new systems, target-state architecture, large refactors, boundary reshaping, platform evolution, service integration design, and migration planning. This is not a code-review skill. Its job is to produce a design that can survive production constraints, organizational growth, and staged delivery.

## When To Use

- Designing a new service, subsystem, or platform.
- Defining bounded contexts, modules, or ownership boundaries.
- Choosing between layered, hexagonal, vertical-slice, modular-monolith, service-based, or event-driven designs.
- Designing ports, adapters, DTOs, integration patterns, and persistence boundaries.
- Planning decomposition of a monolith or repair of architectural drift.
- Producing an ADR, design note, service integration document, or phased rollout plan before implementation.

## Do Not Use This Skill For

- Ordinary implementation tasks that already have settled boundaries.
- PR review or diff review; use `architecture-review` for that.
- Broad enterprise-framework theater with no codebase or product pressure behind it.
- Forcing full clean architecture onto a trivial CRUD path without real volatility or domain complexity.

## Design Stance

- Detect before prescribing. Start from the product, domain, and current system reality.
- Prefer the smallest architecture that protects correctness, changeability, and operational safety.
- Match architecture to system complexity, failure modes, team topology, and expected rate of change.
- Keep business rules independent from frameworks and delivery mechanisms where the domain is non-trivial.
- Treat contracts, configuration, persistence schemas, and user-visible defaults as architecture, not implementation detail.
- Add operational and integration detail only where the context needs it. Do not force service-call, retry, alert, or runbook sections into trivial internal plans with no runtime, integration, money-moving, secret-handling, or operational impact.

## Global Language And Documentation Rules

- Architecture documents are written in Russian by default.
- If higher-priority platform, repository, or user instructions explicitly require another language, follow that instruction and state the deviation when it materially affects the output contract.
- Use clear Russian prose: explain the decision in terms that are useful both to engineers and to business or operations stakeholders.
- Every non-trivial architecture document should include a business-readable layer: what capability, user workflow, operational outcome, cost, risk, or delivery constraint the design affects.
- Keep the engineering layer precise: dependency direction, contracts, data flow, persistence impact, runtime behavior, rollout, and verification should be explicit.
- Add concise examples when they make a contract, workflow, data flow, or failure mode easier to understand. Do not add examples that are only decorative.
- Keep code identifiers, API routes, env vars, config keys, schema names, metrics, and file paths in their original language.
- Follow repository-local architecture templates, headings, and index-update workflows when they exist, but preserve Russian as the default document language unless a higher-priority instruction explicitly requires another language.
- If a repository-local template is structured in another language but does not explicitly mandate that language, reuse its structure and workflow while writing headings and narrative in Russian.
- If the repository has no local template, open `references/output-templates.md`.
- If file paths or modules are only proposals, label them as planned or target structure; do not present them as existing facts.

## Context Acquisition Before Design

For repository-backed design work, read only enough context to design safely.

Prefer this order when available:

1. repository `AGENTS.md` or local engineering contract,
2. the user task and explicit constraints,
3. the nearest architecture index or architecture docs root,
4. task entrypoints, affected modules, and touched contracts,
5. persistence, config, runtime, and integration docs only for the affected areas,
6. planning docs or historical ADRs only if unresolved decisions remain.

Stop expanding context when all of the following are true:

- the business outcome is clear,
- the current-state constraints are clear,
- touched boundaries and contracts are identified,
- non-goals are explicit,
- current docs, code, and observed contracts are reconciled or their drift is explicitly recorded,
- remaining uncertainty can be stated as assumptions instead of requiring more reading.

If the task is greenfield and there is no existing codebase or architecture to inspect, state that explicitly and list the assumptions before designing.

## Core Principles

1. **Dependency direction must be explicit.** Core policy should not depend on delivery or infrastructure details.
2. **Boundaries exist to protect change.** Add one only when it protects a volatile dependency, critical contract, or domain model.
3. **Rich domain where complexity justifies it.** Put domain decisions near domain concepts; keep orchestration in application or use-case layers.
4. **Frameworks live at the edge.** HTTP, ORM, queues, and SDKs are replaceable details unless the product is genuinely framework-centric.
5. **Repository per aggregate or transactional boundary.** Do not mirror every table with a repository by default.
6. **DTOs are for boundaries.** Do not leak ORM models, transport shapes, or persistence records across layers.
7. **Composition root owns wiring.** Dependency injection should be visible and boring.
8. **Architecture must be operable.** Design for observability, error handling, idempotency, retries, rollout, and failure isolation.
9. **Pragmatism beats purity.** For a small CRUD path, a simple layered slice is often better than ceremonial DDD.

## Choose The Architecture By Problem Shape

Select the smallest target shape that protects the real risk:

- simple layered slice when domain rules and integrations are light;
- ports-and-adapters when domain rules, volatile integrations, or test isolation matter;
- vertical slice when product capabilities evolve independently and layer-first coordination is the pain;
- modular monolith before service split when transactional consistency and shared deployment are still useful;
- separate service only for clear scaling, autonomy, trust, failure-isolation, release-cadence, or runtime reasons.

If the choice is non-obvious, or the task asks for detailed tradeoffs, open `references/design-checklists.md`.

## Design Workflow

1. **Clarify the mission.**
   Capture business capability, user-facing outcomes, non-goals, constraints, and quality attributes.
2. **Model the domain.**
   Identify bounded contexts, aggregates, invariants, workflows, and ownership boundaries.
3. **Map the current reality.**
   Record what already exists, what must be preserved, and where drift or pain actually is.
4. **Reconcile evidence.**
   Compare code, docs, configuration, and actual contracts. If they disagree, record what is observed, what is stale, and which fact drives the design.
5. **Choose the target shape.**
   Layered, hexagonal, vertical slices, modular monolith, service split, or event-driven cooperation. State why.
6. **Define boundaries and contracts.**
   Commands, queries, events, DTOs, repository ports, external APIs, config schemas, and persistence seams.
7. **Design runtime behavior.**
   Transaction scope, concurrency model, retries, idempotency, caching, observability, and failure handling.
8. **Design delivery and rollout.**
   Migration strategy, compatibility path, toggles, backfills, dual-write or dual-read concerns, and verification.
9. **Resolve conditional operational coverage.**
   If the design crosses service, context, external-integration, money-moving, secret, runtime, or staged-delivery boundaries, capture the applicable service calls, planned artifacts, affected docs, failure/retry/idempotency rules, redaction rules, alerts, and runbooks.
10. **Design the validation ladder.**
   Define local gates, integration checks, end-to-end/runtime evidence, deployment smoke, browser QA, benchmarks, or adapter checks needed for each stage.
11. **Record tradeoffs.**
   What was rejected and why.
12. **Create the execution ledger.**
   For any staged implementation plan or prompt-pack execution path, define the stage execution ledger path and require it to be updated after every stage.
13. **Define staged execution mode.**
   For any plan intended for prompt-pack execution, name the linked `plan_doc`, expected `prompt_pack_dir`, and `stage_ledger`. Treat Codex Goal mode as optional `goal_driven` execution over those artifacts, not as a requirement to create `GOAL.md`.
14. **Prepare and run the cold-head gate.**
   For every architecture design, ADR, design note, service-integration design, rollout plan, migration plan, development plan, implementation plan, or architecture artifact creation/rewrite/completion/correction, name the artifacts a reviewer must check. When subagents are available, run exactly one automatic read-only cold-head subagent pass before finalizing the design; otherwise run the same checklist locally and label it `cold self-review fallback`. The main agent must apply required fixes and verify them locally before handoff or final response.
15. **Prove traceability.**
   For plan-derived prompt packs, map material decisions and risk controls to stages, expected file/artifact touches, ledger updates, and validation evidence. Anything that cannot be mapped is a blocker, explicit `N/A`, or open decision.

## Conditional Operational Coverage

Use this as a trigger map, not a mandatory section list. Add the detail only when the plan touches the corresponding risk surface.

- **Service calls and integration handoffs**: required when a service, bounded context, adapter, worker, API route, queue, stream, SDK, or external provider participates. Capture who calls whom, sync/async style, contract owner and shape, authn/authz model, timeout, retry/backoff/circuit-breaker policy, degradation path, and what happens on each important failure class.
- **Planned files and artifacts by stage**: required for staged implementation, migration, prompt-pack execution, or plan documents that will be handed to implementation agents. For each stage, name the expected code, config, infra, migration, docs, runbook, prompt, and evidence zones as `existing`, `planned`, or `unknown`.
- **Affected documentation**: required when the design changes a workflow, contract, operational behavior, secret model, strategy behavior, integration, or user/operator surface. Name old/current docs to update, new docs/runbooks to create, and docs indexes to verify. For Roehub exchange/live/execution plans, consider strategy docs, identity/exchange-connection docs, OpenBao or exchange-secret runbooks, operations docs, and exchange-execution runbooks when relevant; do not add those docs if the affected area is unrelated.
- **Errors, retry, and idempotency**: required when the design can perform external side effects, money-moving actions, provider submits, writes to durable state, async processing, or retryable operations. Specify concrete error codes/statuses where known, retryable vs non-retryable classes, idempotency keys or dedupe identity, reconciliation source of truth, and the rule for unknown state. For exchange submit or similar side-effecting calls, do not retry blindly after an unknown result; require reconciliation or provider-state lookup first.
- **Logging and redaction**: required when secrets, credentials, tokens, PII, exchange/provider payloads, order identifiers, account identifiers, or operational evidence may appear in logs, metrics, traces, ledgers, or reports. State what may be logged, what must be hashed/summarized, and what is forbidden.
- **Alerts and operational monitoring**: required for runtime services, workers, queues, schedulers, exchange execution, target-host operations, or user-impacting degradation. Define alert rules, trigger thresholds or symptoms, target metrics/log signals, severity, owner, and runbook actions.

For production rollout plans, avoid ambiguous topology options in executable stages. If the design says "reuse existing worker or create a new app", either choose the default target topology in the plan or mark the decision as an explicit blocker with the evidence needed to decide before implementation.

## Mandatory Cold-Head Gate

Every architecture artifact created, reviewed, rewritten, extended, or fixed with this skill must pass the cold-head gate using `architecture-review/references/cold-head-plan-prompt-pack-review.md` before it is reported as ready.

Run exactly one automatic independent read-only cold-head subagent pass when subagents are available. If subagents are unavailable, run the same checklist locally and label it `cold self-review fallback`. After the review, the main agent must incorporate every Blocker and relevant High finding before handing the plan to `prompt-manager`; do not launch repeated reviewer passes unless the user explicitly requests another independent review.

Before any final response that reports an architecture artifact as ready, final, complete, finished, `готов`, `завершен`, or `подготовлен`, include this exact structured receipt block:

```text
Cold-head review: completed
Mode: independent subagent | cold self-review fallback
Review scope: ...
Review instructions: architecture-review/references/cold-head-plan-prompt-pack-review.md
Verdict: Release | Release after fixes | Block
Blockers fixed: ...
Local follow-up check: completed | not needed | blocked
Residual risks: ...
```

Do not use readiness language for an architecture document, ADR, design note, service-integration design, rollout plan, migration plan, development plan, or implementation plan unless that structured receipt is present. If the cold-head pass is unavailable or unresolved, state that the artifact is not ready and report the blocker.

For staged plans or designs that will be handed off to `prompt-manager`, ensure the design provides:

- stage ledger path and update rule;
- execution mode: `manual_sequential` by default, `goal_driven` only when the user wants Codex Goal mode/autocontinuation;
- linked `plan_doc`, expected `prompt_pack_dir`, and `stage_ledger`, with no default requirement to create `GOAL.md`;
- per-stage file/artifact manifest with code, config, infra, migrations, docs, runbooks, prompt artifacts, and evidence targets;
- traceability from material architecture requirements to stages, file/artifact touches, ledger fields, and validation evidence;
- fixed runtime topology or explicit `unknown-blocker`;
- service-call table with auth, timeout, retry/backoff, idempotency/dedupe, error behavior, and unknown-state rule where applicable;
- affected old/current docs and new docs/runbooks;
- validation ladder with real-boundary evidence for non-trivial stages;
- redaction and secret-handling rules for ledgers, logs, reports, screenshots, traces, and provider payloads.

If any required item is missing, record it as a blocker or open decision instead of relying on the prompt pack to infer it later.

## Decision Ledger

For each key decision, capture:

- `decision`: what changes in the target architecture;
- `why now`: product, operational, contract, or maintainability pressure;
- `business effect`: which business capability, user workflow, operational outcome, cost, or risk changes;
- `alternatives rejected`: the realistic options and why they lose here;
- `contracts affected`: public API, port, DTO, persistence, config, cache identity, runtime workflow, or none;
- `migration / rollback`: how the system moves safely from current state to target state;
- `stage ledger`: where execution status and handoff facts will be recorded when the decision is implemented through stages;
- `execution mode`: manual sequential by default, or goal-driven when the user wants the prompt pack executed as a Codex goal;
- `validation ladder`: local gates plus the real-boundary/end-to-end evidence required before the decision is accepted;
- `conditional operations`: service calls, affected docs, planned artifacts by stage, error/retry/idempotency, redaction, alerts, or `not applicable` with a short reason;
- `verification`: tests, runtime checks, benchmarks, docs checks, or manual evidence needed.

Do not present proposed paths, modules, or contracts as existing facts.

## Output Mode Selection

Choose the artifact deliberately:

- `ADR` when one primary decision, its alternatives, and consequences are the artifact.
- `Архитектурное решение` when you need a target-state note for a subsystem, boundary, or design change.
- `Дизайн интеграции сервиса` when the main question is how one service fits into the wider system.
- `План внедрения` when the main need is sequencing implementation, migration, or rollout.
- `Решение + внедрение` when the main question is how to reshape a subsystem, bounded context, or module and roll the change out in phases.
- `Интеграция + внедрение` when the user asks both how the service fits and how to roll it out.

Default rule:

- if the task is target-state redesign of a subsystem, bounded context, or module plus staged implementation, use a combined package:
  - primary artifact: `Архитектурное решение`,
  - secondary artifact: `План внедрения`,
  - required handoff artifact: `Журнал выполнения stages`,
  - merge them into one document only when the scope stays readable and duplication is low;
- if both target-state fit and staged implementation matter, use a combined package:
  - primary artifact: `Дизайн интеграции сервиса`,
  - secondary artifact: `План внедрения`,
  - required handoff artifact: `Журнал выполнения stages`,
  - merge them into one document only when the scope stays readable and duplication is low.

For full templates, open `references/output-templates.md`.

## Bounded Context And Module Design

- Prefer boundaries around business capability, not around technical nouns.
- One bounded context should own its internal model and invariants.
- Cross-context interaction should happen through an ACL, published contract, or explicit translation layer.
- Shared kernel should stay small: primitives, cross-cutting types, and stable contracts only.
- If two modules constantly change together, they probably are not separate modules yet.
- If one module needs another module's internal model to work, the boundary is wrong or missing translation.

## Dependency And Layer Rules

- Domain must not import infrastructure or transport.
- Application or use-case layer may depend on domain plus ports and boundary DTOs.
- Adapters implement ports and translate between external shapes and internal models.
- Routers, controllers, and handlers should validate, authorize, call application logic, and map responses; they should not hold business rules.
- Repository interfaces belong near the application or domain boundary they serve, not inside infrastructure.

## Migration Planning Rules

- Prefer phased migration over big-bang rewrites.
- Preserve external contracts unless change is deliberate and migration is explicit.
- Start by extracting seams around one capability, one workflow, or one boundary.
- Use strangler patterns for incremental replacement where possible.
- For schema or contract changes, specify backward-compatibility and rollback strategy.
- Call out dual-write, dual-read, replay, and backfill risks explicitly.
- Tie each migration step to verification evidence, not hope.
- For prompt-pack or staged-agent execution, create a stage execution ledger using the repository template when available, and require every stage to update status, blockers, evidence, contract impact, and next-stage handoff notes.
- Do not define stage acceptance as tests-only unless the stage is trivial and internal-only. For any contract, persistence, browser-visible, runtime, ops, performance, integration, or delivery impact, require a real-boundary or end-to-end validation surface.

## Validation Ladder Rules

For every non-trivial architecture plan, define validation in layers:

1. **Local correctness gates**: lint, type checks, focused unit/integration tests.
2. **Boundary validation**: API/use-case smoke, DTO mapping, repository/database integration, migration check, browser runtime QA, or adapter-safe smoke depending on the changed surface.
3. **Target-runtime validation**: CI/deploy status, Mac Studio or target-host smoke, health checks, metrics, file/config parity, Monit/launchd evidence, or production-safe smoke when the plan is meant to ship.
4. **Specialized evidence**: benchmark/profile for performance-sensitive paths, security/eval harness for trust-boundary changes, or failure-mode drill for resilience changes.

Tests-only validation is a documented exception, not the default. If a plan uses it, state why no real-boundary, runtime, browser, persistence, ops, performance, or delivery surface is affected.

Each rollout stage should state:

- local gates;
- required real-boundary/end-to-end evidence;
- acceptance blocker if that evidence cannot be collected;
- where the evidence will be recorded in the stage ledger.

## Review Your Design Before Presenting It

Check:

- Is the architecture proportional to the problem?
- Is dependency direction clear and enforceable?
- Are business invariants owned in one place?
- Are contracts, DTOs, and persistence seams explicit?
- Are source-of-truth and ownership boundaries explicit?
- Are failure modes, observability, and rollout addressed?
- When service or external calls exist, are caller/callee, contract, auth, timeout/retry, and failure behavior explicit?
- For side-effecting external submits, does unknown state require reconciliation instead of blind retry?
- Are planned code/config/infra/docs/runbook artifacts mapped by stage when the plan is staged?
- Can each material architecture requirement be traced to a stage, expected artifact, ledger update, and validation evidence?
- Are affected docs, redaction rules, alerts, and runbook actions named where the context requires them?
- Is runtime topology fixed enough for execution, or is the unresolved choice explicitly marked as a blocker?
- Is the plan ready for cold-head review before prompt generation, with artifacts and entrypoints named?
- Does the final response include the structured cold-head receipt block before claiming the artifact is ready, final, complete, `готов`, `завершен`, or `подготовлен`?
- Does the migration path preserve recoverability?
- Did you propose only the minimum architecture needed?
